## NET-DNS-001 · 域名怎样变成可连接的地址

> [!question] 问题 1 / 6
> 输入一个域名，程序在 connect 之前怎样得到候选地址？缓存命中与权威答案有什么区别？

**原帖明确考点：**[字节懂车帝后台一面](https://www.nowcoder.com/discuss/353159577019555840)。YuYoung32 / 牛客，2022-04-20 发布，C++ 后台岗位；搜索索引可读，原页本次未能取得正文。原帖明确提到“DNS 如何查找 www.xx.com”。

**本库扩展：**题面条件、追问与代码均为教学设计。详细学习：[[学习/2026-11-02/01-DNS解析与缓存]]。

> [!hint]- 卡住时再看提示
> 域名是给人用的名字。先分清协议承诺与业务结果。

> [!tip]- 点击查看参考解答
> **面试口述（约 30–90 秒）**：先通过系统解析接口把域名转换为候选地址，结果可能来自本地配置或缓存，也可能经过递归 DNS 查询；缓存受 TTL 等策略约束。随后对候选地址建连，连接成功和 TLS 身份验证是后续独立步骤。
>
> **场景与边界**：交易网关连接配置的是域名时，重连必须处理地址变化、解析失败与超时；不能把一次解析所得 IP 永久视为不变。 hosts 文件、缓存、DNS64、多个地址及系统解析配置都会改变观察结果。DNS 查到地址不代表服务可连接，也不代表远端身份已验证。
>
> **核对技术依据**：[RFC 1034 §4–5：权威、缓存与解析器](https://www.rfc-editor.org/rfc/rfc1034.html)；[Linux getaddrinfo(3)](https://man7.org/linux/man-pages/man3/getaddrinfo.3.html)（2026-11-02 核对）。

> [!info]- 深挖与追问（选学）
> 问：DNS 一定每次都从根服务器查起吗？答：不一定，本地/递归缓存可能直接给出答案，解析器配置也因系统而异。

## NET-SOCKET-001 · 服务器怎样接入一条 TCP 连接

> [!question] 问题 2 / 6
> 服务端要按什么顺序调用 socket、bind、listen、accept？监听 fd 与连接 fd 分别做什么？

**原帖明确考点：**[招银网络技术一面](https://www.nowcoder.com/discuss/872488632311939072)。英俊的小松鼠面试中 / 牛客，页面显示 04-11，年份与首发时间未显示，C++ 岗；搜索索引可读，原页本次未能取得正文。原帖明确写“TCP 三次握手流程，对应的 socket API”。

**本库扩展：**题面条件、追问与代码均为教学设计。详细学习：[[学习/2026-11-02/02-socket服务端链路]]。

> [!hint]- 卡住时再看提示
> socket 是内核提供的通信端点。先分清协议承诺与业务结果。

> [!tip]- 点击查看参考解答
> **面试口述（约 30–90 秒）**：服务端 socket、bind、listen、accept；客户端 socket、connect。accept 返回独立的已连接 fd，原监听 fd 仍可接别的连接。三次握手由 TCP 栈处理，accept 的语义是取得已到达的连接，不能把 connect 写成服务端接收操作。
>
> **场景与边界**：行情接入服务监听固定端口，accept 后为每个连接建立状态对象；对端断开时关闭连接 fd，服务退出时再关闭监听 fd。 Linux listen 的 backlog 主要限制完成握手后等待 accept 的队列长度，受 somaxconn 等限制；不应把它直接等同于并发连接总数。示例未实现错误重试、非阻塞 I/O 或多客户端服务。
>
> **核对技术依据**：[Linux listen(2)](https://man7.org/linux/man-pages/man2/listen.2.html)；[Linux accept(2)](https://man7.org/linux/man-pages/man2/accept.2.html)（2026-11-02 核对）。

> [!info]- 深挖与追问（选学）
> 问：listen backlog 等于最大在线用户数吗？答：不是，它限制等待 accept 的已建立连接队列，具体上限还受系统配置影响。

## NET-HTTPMSG-001 · HTTP/1.1 怎样知道一条消息结束了

> [!question] 问题 3 / 6
> HTTP/1.1 报文的起始行、字段、空行和正文怎样分开？看到 Content-Length=5 时已收到 3 字节怎么办？

**原帖明确考点：**[字节懂车帝后台一面](https://www.nowcoder.com/discuss/353159577019555840)。YuYoung32 / 牛客，2022-04-20 发布，C++ 后台岗位；搜索索引可读，原页本次未能取得正文。原帖明确问“怎么知道 HTTP 内容传完了没”。

**本库扩展：**题面条件、追问与代码均为教学设计。详细学习：[[学习/2026-11-02/03-HTTP报文边界]]。

> [!hint]- 卡住时再看提示
> 起始行写请求方法、目标与版本，或响应版本与状态。先分清协议承诺与业务结果。

> [!tip]- 点击查看参考解答
> **面试口述（约 30–90 秒）**：HTTP/1.1 报文先由起始行和字段区组成，空行后才是可能存在的正文。正文是否完成按 RFC 9112 的定界规则判断，固定长度时数够 Content-Length 指定的八位字节；一次 recv 可能不足，也可能多出下一条消息。
>
> **场景与边界**：网关或订单 API 服务若把半条请求当完整处理，会错误执行；如果盲信互相冲突的长度字段，还会出现前后端解释不一致的风险。生产环境应使用成熟 HTTP 实现。 完整 HTTP 解析还要处理大小写不敏感的字段名、重复字段、chunked、方法/响应特例、头部长度上限及恶意输入。本例绝不是可上网部署的服务器。
>
> **核对技术依据**：[RFC 9112 §2、§6：消息语法与定界](https://www.rfc-editor.org/rfc/rfc9112.html)（2026-11-02 核对）。

> [!info]- 深挖与追问（选学）
> 问：Content-Length 与 Transfer-Encoding 同时出现怎么办？答：发送方不得这样发送，接收方需按 RFC 的优先级与错误处理规则处置，不能随意挑一个信。

## NET-HTTPMETHOD-001 · GET、POST、PUT 的语义和幂等性

> [!question] 问题 4 / 6
> “安全”与“幂等”分别是什么意思？GET、POST、PUT 在一次超时重试中应怎样判断风险？

**原帖明确考点：**[猿辅导 C++ 后端一面](https://www.nowcoder.com/discuss/353156713845039104)。WenKoKu / 牛客，2020-08-07 编辑，C++ 后端岗位；原页正文全文可读。原帖列出 HTTP 请求方式、GET/POST 区别及各方法的幂等性。

**本库扩展：**题面条件、追问与代码均为教学设计。详细学习：[[学习/2026-11-02/04-HTTP方法与幂等]]。

> [!hint]- 卡住时再看提示
> 安全方法指请求的目标语义是只读。先分清协议承诺与业务结果。

> [!tip]- 点击查看参考解答
> **面试口述（约 30–90 秒）**：安全是约定不会请求改变服务端状态；幂等是相同请求重复执行后的预期效果与一次相同。GET 安全且幂等，PUT/DELETE 幂等，POST 默认不能假定幂等。超时重试要同时看方法语义和业务侧请求 ID。
>
> **场景与边界**：下单 API 超时后，不能因为 TCP 连接断开就认定订单没提交。客户端应携带业务请求 ID，服务端记录处理结果并按协议提供查询/去重。 若服务端违背方法语义，GET 也可能产生副作用；规范定义与实际实现需分别检查。POST 可以被应用设计成幂等，但 HTTP 方法名本身不保证。
>
> **核对技术依据**：[RFC 9110 §9.2–9.3：安全、幂等与方法语义](https://www.rfc-editor.org/rfc/rfc9110.html)（2026-11-02 核对）。

> [!info]- 深挖与追问（选学）
> 问：DELETE 第二次得到 404，是否说明它不幂等？答：不说明。资源最终已被删除，响应可以不同。

## NET-HTTPVERSION-001 · HTTP 长连接与 HTTP/2 多路复用

> [!question] 问题 5 / 6
> HTTP/1.1 的连接复用与 HTTP/2 的多路复用各解决什么问题？为什么一条 TCP 上的不同流仍会互相影响？

**原帖明确考点：**[美团一面凉经](https://www.nowcoder.com/discuss/353158512492617728)。尘埃飞舞 / 牛客，2021-09-14 编辑，C++ 相关开发面试；搜索索引可读，原页本次未能取得正文。原帖明确列“HTTP 1.0/1.1 长短连接、2.0 新特性、怎么实现长连接”。

**本库扩展：**题面条件、追问与代码均为教学设计。详细学习：[[学习/2026-11-02/05-连接复用与HTTP2]]。

> [!hint]- 卡住时再看提示
> 长连接指完成一个请求/响应后保留传输连接供后续使用。先分清协议承诺与业务结果。

> [!tip]- 点击查看参考解答
> **面试口述（约 30–90 秒）**：HTTP/1.1 的持久连接复用一条 TCP 连接做多个请求，减少重复连接；HTTP/2 则在一条连接内用流 ID 与二进制帧交错传输多个请求/响应，缓解应用层串行等待。不过底层 TCP 仍要求有序交付，丢包会影响该连接上的流。
>
> **场景与边界**：C++ API 网关面对多并发请求时，复用连接可减少反复建连成本；HTTP/2 可让同一连接承载多流，但还要观察服务端限流、流控、TCP 丢包和真实延迟。 HTTP/1.1 不是强制永远不断开，HTTP/2 也不是零延迟。HTTP/2 的旧版优先级树细节已被 RFC 9113 修订，不宜照旧资料背诵。不能把 HTTP keep-alive 与 TCP SO_KEEPALIVE 混为一谈。
>
> **核对技术依据**：[RFC 9112 §9：HTTP/1.1 连接管理](https://www.rfc-editor.org/rfc/rfc9112.html)；[RFC 9113 §5、§9：流与持久连接](https://www.rfc-editor.org/rfc/rfc9113.html)（2026-11-02 核对）。

> [!info]- 深挖与追问（选学）
> 问：HTTP/2 为什么还可能有队头阻塞？答：它消除了 HTTP/1.1 级别的一部分串行阻塞，但底层 TCP 丢字节时后续字节仍需等待重传。

## NET-TLS-001 · HTTPS 怎样建立加密且可认证的连接

> [!question] 问题 6 / 6
> HTTPS 中 TLS 握手解决什么？为什么拿到证书还要验证域名与信任链？TLS 1.3 可以简化成“公钥加密对称密钥”吗？

**原帖明确考点：**[招银网络 C++ 后端一面](https://www.nowcoder.com/feed/main/detail/fa03b7d8938540c09d5442b60b758ef0)。吃西瓜的飞象 / 牛客，2024-09-06 编辑，C++ 后端岗位；搜索索引可读，原页本次未能取得正文。原帖明确列“HTTP 和 HTTPS 的区别，HTTPS 怎么建立加密传输”。

**本库扩展：**题面条件、追问与代码均为教学设计。详细学习：[[学习/2026-11-02/06-HTTPS与TLS握手]]。

> [!hint]- 卡住时再看提示
> TLS 是保护传输的协议。先分清协议承诺与业务结果。

> [!tip]- 点击查看参考解答
> **面试口述（约 30–90 秒）**：HTTPS 通常是在 TCP 上先完成 TLS，再传 HTTP。TLS 1.3 用密钥交换与派生建立会话密钥，证书和握手证明用于认证服务器；客户端还要核对证书链与目标域名。此后用认证加密保护应用数据。加密连接不等于业务提交成功。
>
> **场景与边界**：交易后台或管理 API 若跳过证书验证，即使流量被加密，也可能与冒充的服务器通信；应使用成熟 TLS 库并正确配置服务器名验证。 TLS 只保护端点间的传输，不能自动保证业务请求被正确执行。证书有信任链、有效期、名称匹配等多个检查。0-RTT 的重放边界不在本日示例内；不要手写生产 TLS。
>
> **核对技术依据**：[RFC 8446 §2、§4：TLS 1.3 握手](https://www.rfc-editor.org/rfc/rfc8446.html)；[RFC 9525：TLS 服务身份校验](https://www.rfc-editor.org/rfc/rfc9525.html)（2026-11-02 核对）。

> [!info]- 深挖与追问（选学）
> 问：证书验证失败还能继续发敏感请求吗？答：应拒绝该连接或按明确的测试环境策略处理，生产客户端不能静默忽略。

**本库自拟练习**，不是面经原题，也不计第七个新目标。详解与代码：[[学习/2026-11-02/07-练习-请求重试判定]]。

> [!hint]- 卡住时再看
> 超时不能证明服务端没有提交；先给同一逻辑请求一个稳定身份。

> [!tip]- 点击查看参考解答
> 无业务 ID 时不能因连接超时就盲目再次创建订单，应先查业务状态或走人工/协议定义的恢复流程；有服务端持久去重记录和稳定请求 ID 时，可用同一 ID 重试，服务端返回已有处理结果。仅在内存里去重不够生产可靠性，重启和并发路径还要保证原子性与持久性。
