## BUILD-STAGE-001 · 从源码到可执行文件：四个阶段

> [!question] 问题 1 / 7
> 一个 main.cpp 包含头文件并调用函数，执行 g++ main.cpp -o app 时，从源文件到运行文件经历什么？-E、-S、-c 分别停在哪里？

**题型来源与边界：**[字节跳动 C++ 客户端实习面经](https://www.nowcoder.com/discuss/353156251678875648)。字节跳动 C++ 客户端实习候选人明确记录“C++ 代码到可执行程序的过程，详细描述四个阶段”；本题的命令与定位场景自行设计。 详解 [[学习/2026-10-28/01-编译四阶段|专题学习]]。

> [!hint]- 卡住时再看提示
> 先把 #include 展开、生成汇编、产出 .o、合并符号分开。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**预处理处理 #include、条件编译和宏，得到翻译单元；编译将 C++ 语义分析并生成汇编；汇编形成含符号与重定位信息的目标文件；链接把多个目标文件和需要的库组合并解析引用，生成可执行文件。在 GCC 驱动中 -E 停在预处理、-S 停在汇编文本、-c 停在目标文件。编译通过不代表链接会通过，程序启动加载也不等于编译。
>
> **易错边界：**“四阶段”是常用教学模型；驱动可合并内部步骤，优化与 LTO 也会改变实际执行时机。
>
> **核对来源：**[GCC Overall Options](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)。

> [!info]- 深挖与追问
> 追问：某行头文件没有被找到属于哪里？预处理阶段。函数只声明未定义为何能编译？调用点类型检查可过，最终链接找不到定义。

## BUILD-ODR-001 · 声明、定义、翻译单元与 ODR

> [!question] 问题 2 / 7
> 头文件中写 int counter = 0，两个 .cpp 都包含它，会出什么问题？如何组织声明与定义？C++17 inline 变量何时有用？

**题型来源与边界：**[秋招历程](https://www.nowcoder.com/discuss/353154167852179456)。美团候选人复盘明确记录了“undefined reference”原因和 static 成员变量；题面中的双文件 ODR 故障是自行增加的工程变式。 详解 [[学习/2026-10-28/02-声明定义与ODR|专题学习]]。

> [!hint]- 卡住时再看提示
> 分清 extern int x; 与 int x = 0;，再看被几个翻译单元包含。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**`extern int counter;` 是变量声明；`int counter = 0;` 是定义。把普通定义放进被两个 .cpp 包含的头文件，会让两个翻译单元都产生定义，通常链接报告 multiple definition。典型做法是头文件声明、一个 .cpp 定义；C++17 可用 `inline int counter = 0;` 在头文件提供满足相应条件的多翻译单元定义。未定义引用则通常是声明能见到，但最终没有可链接的定义或相关目标文件未进链接。
>
> **易错边界：**ODR 违规不总会被诊断；不同翻译单元的宏配置让 inline 定义不一致，也可能落入无诊断要求的错误。
>
> **核对来源：**[C++17 [basic.def]](https://timsong-cpp.github.io/cppwp/n4659/basic.def)、[C++17 [basic.def.odr]](https://timsong-cpp.github.io/cppwp/n4659/basic.def.odr)。

> [!info]- 深挖与追问
> 追问：头文件保护能解决跨两个 .cpp 的重复定义吗？不能，它只防同一翻译单元重复包含。`static` 放头文件会形成各翻译单元自己的内部链接实体，不是共享同一变量。

## BUILD-TEMPLATE-001 · 模板实例化与“头文件看得到定义”

> [!question] 问题 3 / 7
> 模板函数在头文件只有声明，实现在 .cpp，另一个 .cpp 调用时为何常出现 undefined reference？显式实例化怎样改变布局？

**题型来源与边界：**[字节跳动 C++ 客户端实习面经](https://www.nowcoder.com/discuss/353156251678875648)。字节跳动 C++ 客户端复盘问到源码到可执行程序过程；模板跨翻译单元故障是据此自行设计的工程变式，原帖未直接问模板。 详解 [[学习/2026-10-28/03-模板实例化|专题学习]]。

> [!hint]- 卡住时再看提示
> 调用模板时编译器需要为具体 T 产生代码，问“定义在哪里可见”。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**模板是生成具体特化的模式。对 `twice<int>` 的隐式实例化通常要在实例化点看到定义，所以常把模板定义放头文件。另一种布局是在实现 `.cpp` 中定义模板并显式实例化所需类型，在调用处只给声明，必要时用 `extern template` 抑制重复隐式实例化。此时只支持已显式实例化的类型，漏一个类型会造成链接失败。
>
> **易错边界：**`extern template` 本身不生成实现，必须在程序别处提供匹配的显式实例化定义；是否真正“重复生成”也受实现与链接器合并策略影响。
>
> **核对来源：**[C++17 [temp.inst]](https://timsong-cpp.github.io/cppwp/n4659/temp.inst)、[C++17 [temp.explicit]](https://timsong-cpp.github.io/cppwp/n4659/temp.explicit)。

> [!info]- 深挖与追问
> 追问：`twice<double>` 可否自动调用只显式实例化 int 的库？不能假定可以；若调用点看不到模板定义且库里也无 double 实例，链接将缺实现。

## BUILD-ARCHIVE-001 · 静态库、归档抽取与链接顺序

> [!question] 问题 4 / 7
> Linux 上 libmath.a 与 main.o 链接时，为什么 `g++ libmath.a main.o` 可能找不到符号，而 `g++ main.o libmath.a` 可以？静态库与普通 .o 有何区别？

**题型来源与边界：**[字节跳动 C++ 客户端实习面经](https://www.nowcoder.com/discuss/353156251678875648)。字节跳动 C++ 客户端复盘明确记录静态库/动态库区别；题面的 GNU ld 归档顺序是自行增加的工程变式。 详解 [[学习/2026-10-28/04-静态库与链接顺序|专题学习]]。

> [!hint]- 卡住时再看提示
> 想象链接器沿命令行经过归档时，只抽取当下需要的成员。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**静态库 `.a` 是目标文件归档，不是运行时独立加载的库。GNU ld 通常按命令行位置扫描归档：先出现引用 `main.o`，再出现 `libmath.a`，归档成员才能被需要的未定义符号拉入；反过来先扫描归档，当时尚无对应未定义引用，就可能不抽取该成员，之后不自动回头。直接给出的普通 `.o` 与按需求抽取的归档不同。
>
> **易错边界：**这是 GNU ld 典型规则，不是 C++ 标准；其他链接器及参数可能不同。循环依赖可用重排、重复库或 group 解决，但应先理清依赖。
>
> **核对来源：**[GNU ld Options: archives](https://sourceware.org/binutils/docs/ld/Options.html)、[GCC Link Options](https://gcc.gnu.org/onlinedocs/gcc/Link-Options.html)。

> [!info]- 深挖与追问
> 追问：`-L` 和 `-l` 分别做什么？`-L` 增加链接时库搜索目录，`-lname` 请求库；两者均不能保证程序运行时找到共享库。

## BUILD-SHARED-001 · 动态库搜索、PIC 与 extern C 边界

> [!question] 问题 5 / 7
> 程序链接时找到了 libquote.so，启动却提示找不到它；该如何排查？`-fPIC` 和 `extern "C"` 各解决哪一类问题？

**题型来源与边界：**[趋势科技 C++ 开发面经](https://www.nowcoder.com/feed/main/detail/0c8a660a2aed49fdbf9bc695a4fa705b)。趋势科技 C++ 开发候选人明确记录了静动态库使用过程和动态库查找；PIC、extern C 与排查命令是自行扩展。 详解 [[学习/2026-10-28/05-动态库与ABI|专题学习]]。

> [!hint]- 卡住时再看提示
> 把链接时搜索路径、运行时装载路径、符号名规则分成三件事。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**`-L` 帮助构建时链接器定位库，不负责运行时搜索。Linux ELF 的动态装载器依赖 DT_NEEDED、RPATH/RUNPATH、环境变量及系统目录等规则找共享对象，应查看 `readelf -d` 和系统装载规则。`-fPIC` 让支持的平台生成适合共享库的地址无关代码；`extern "C"` 给函数指定 C 语言链接规则，常用于跨 C/C++ 的符号边界，但不保证整个 C++ ABI 兼容，也不使 C++ 类可直接作为 C 接口。
>
> **易错边界：**`ldd` 对不可信文件不宜随意执行；这里的教学程序可用 `readelf -d` 先看依赖。RUNPATH 对间接依赖的行为与 RPATH 不同，按平台手册核对。
>
> **核对来源：**[Linux ld.so(8)](https://man7.org/linux/man-pages/man8/ld.so.8.html)、[GCC PIC options](https://gcc.gnu.org/onlinedocs/gcc/Code-Gen-Options.html)、[C++17 [dcl.link]](https://timsong-cpp.github.io/cppwp/n4659/dcl.link)。

> [!info]- 深挖与追问
> 追问：把函数声明改成 `extern "C"` 能解决“找不到 .so 文件”吗？不能；那是库文件搜索问题。名字能解析也不等于调用约定、对象布局和异常跨边界安全。

## BUILD-CMAKE-001 · CMake target 与依赖传播

> [!question] 问题 6 / 7
> 一个 CMake 项目里，头文件需要某宏，且调用者也需要看到它；target_compile_definitions 应用 PRIVATE、PUBLIC 还是 INTERFACE？target_link_libraries 的作用只是拼 -l 吗？

**题型来源与边界：**[字节跳动 C++ 客户端实习面经](https://www.nowcoder.com/discuss/353156251678875648)。字节跳动候选人明确问了源码到可执行程序过程；CMake target 属性传播是为了读懂实际项目而自行设计的训练题，原帖未问 CMake。 详解 [[学习/2026-10-28/06-CMake目标与依赖|专题学习]]。

> [!hint]- 卡住时再看提示
> PRIVATE 给自身，INTERFACE 给使用者，PUBLIC 给两边。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**CMake 以 target 表达可执行文件、库及其使用要求。某宏若库自身编译和调用者头文件都要用，应使用 PUBLIC；仅库实现要用选 PRIVATE；只让使用者知道选 INTERFACE。`target_link_libraries` 不只是文本拼 `-l`，还表达目标之间的依赖及使用要求传播，具体传递由作用域决定。构建目录与源码目录分开，便于检查生成命令和重建。
>
> **易错边界：**不要把所有 include 目录、宏和库都设 PUBLIC；泄露无关依赖会增加耦合和重编译范围。实际属性传播以所用 CMake 版本和 target 类型核对。
>
> **核对来源：**[CMake 官方教程：target 与作用域](https://cmake.org/cmake/help/latest/guide/tutorial/Getting%20Started%20with%20CMake.html)、[target_link_libraries](https://cmake.org/cmake/help/latest/command/target_link_libraries.html)。

> [!info]- 深挖与追问
> 追问：消费者引用头文件中出现的第三方类型时，库对第三方头文件依赖能否只标 PRIVATE？通常不够，消费者也需要相应使用要求。

## EX-20261028-001 · 练习：诊断一次 undefined reference

> [!question] 小练习 7 / 7
> 先运行默认源码；再用 `-DDEMO_MISSING_DEFINITION` 编译，记录报错属于哪个阶段。最后解释“补上声明”和“补上定义”哪个能修复它，并给出排查步骤。

**题型来源与边界：**[秋招历程](https://www.nowcoder.com/discuss/353154167852179456)。美团候选人明确记录了静态链接时 undefined reference 的问法；具体代码和修复步骤均为自行设计。 详解 [[学习/2026-10-28/07-练习-链接错误诊断|专题学习]]。

> [!hint]- 卡住时再看提示
> 声明足以让编译器接受调用；链接器还要寻找实现。

> [!tip]- 点击查看标准解答
> **面试口述（30–90 秒）：**默认模式中 `rate(int)` 有定义，输出 10。加宏时依然有 `rate(int)` 声明，但定义被条件编译排除，所以通常在链接时报 undefined reference。再次增加声明不会创造实现；需要提供签名一致的定义、把对应 `.o`/库加入链接，或修正库顺序。先确认完整符号签名，再确认定义是否生成，最后确认目标文件和库路径/顺序。
>
> **易错边界：**诊断文本因工具链不同而变化；非 GNU 平台不能把报错文字和命令写成语言保证。
>
> **核对来源：**[GCC Link Options](https://gcc.gnu.org/onlinedocs/gcc/Link-Options.html)、[GNU ld Options](https://sourceware.org/binutils/docs/ld/Options.html)。

> [!info]- 深挖与追问
> 追问：若函数定义在 `.so` 里，但启动时找不到 `.so`，这与本题的链接失败同一阶段吗？不是，前者属于运行时装载。
