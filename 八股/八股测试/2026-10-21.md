## CPP-INHERIT-001 · 继承与组合分别表达什么

> [!question] 问题 1 / 6 · 先确定类型关系
> 在 C++17 中，`class LiveFeed : public Feed` 表示什么？一个派生类对象中，基类部分在哪里？
>
> 请解释 `public` / `protected` / `private` 成员，以及公有、保护、私有继承的区别。`class D : B` 与 `struct D : B` 默认是否相同？
>
> 行情处理器需要一个日志器，应该优先考虑“继承日志器”还是“包含 / 引用日志器”？说明理由。

学习入口：[[学习/2026-10-21/01-继承与组合]]。

> [!hint]- 卡住时再看提示
> 分开看两处访问说明符：一处写在类内部的成员前，一处写在继承列表里。再问业务对象究竟“是一种什么”，还是“需要使用什么”。

> [!tip]- 标准解答
> **面试口述**
>
> 公有继承可以表达“派生类是一种基类”，派生对象包含基类子对象，并可以在公开、无歧义等条件满足时转换为相应基类的指针或引用。组合表达“对象具有或使用另一个对象”，不要求它们是同一种类型。
>
> 成员的 public / protected / private 控制谁能访问；继承说明符进一步影响继承来的 public、protected 成员在派生类中的可访问性，以及基类转换的可访问性。基类 private 成员仍在基类子对象中，派生类普通成员函数不能直接按名字访问它们。
>
> 未写继承说明符时，class 默认 private 继承，struct 默认 public 继承；类内成员默认访问权限也分别是 private 和 public。这是两个相关但不同的位置。
>
> **用途与反例**
> - 不同行情源都能满足“行情源”的约定，可以考虑公有继承表达接口关系。
> - 行情处理器使用日志器，通常用成员或引用表达组合 / 协作，不应只为复用日志方法就声称处理器“是一种日志器”。
> - 基类构造先于派生类自己的成员和构造函数体；成员按声明顺序初始化，不按初始化列表书写顺序任选。
> - 基类数据并不会因为访问权限变成 private 就从对象里消失。
>
> **核对来源**：[N4659 · class.derived](https://timsong-cpp.github.io/cppwp/n4659/class.derived)、[class.access.base](https://timsong-cpp.github.io/cppwp/n4659/class.access.base)、[class.base.init](https://timsong-cpp.github.io/cppwp/n4659/class.base.init)。

> [!info]- 深挖与追问
> **public 继承就自动保证业务上可以替换吗？**
> 不自动保证。语言提供转换和调用规则，接口对输入、输出与行为的约定仍要由实现遵守；不能靠继承语法使不兼容的行为变得合理。
>
> **private 继承完全不能用吗？**
> 可以使用，它能表达某些实现关系，但不向外部提供一般的公有基类转换。初学阶段先会区分它与“在类里放一个成员”，不要把它默认当成公有多态接口。

- [ ] 能把成员访问权限、继承方式和 is-a / has-a 分开解释。

## CPP-VIRTUAL-001 · 同一个对象，经不同类型调用时选哪个函数

> [!question] 问题 2 / 6 · 静态类型与动态类型
> 按 C++17、单继承、对象均存活考虑，以下是声明与调用片段。返回的字符串只是帮助辨认函数的标签。
>
> ```cpp
> struct Base {
>     const char* plain() const { return "Base plain"; }
>     virtual const char* kind() const { return "Base virtual"; }
> };
>
> struct Derived : Base {
>     const char* plain() const { return "Derived plain"; }
>     const char* kind() const override { return "Derived virtual"; }
> };
>
> Derived object;
> Base& view = object;
> // view.plain()
> // view.kind()
> // object.plain()
> // view.Base::kind()
> ```
>
> 四次调用各选择哪个函数？静态类型与动态类型分别指什么？虚函数是否意味着标准规定每个对象里一定有一个固定大小的虚表指针？

学习入口：[[学习/2026-10-21/02-虚函数与动态绑定]]。

> [!hint]- 卡住时再看提示
> `view` 是哪个类型的引用？它实际引用哪个完整对象？再检查调用是否是虚函数，以及有没有显式写出基类限定名。

> [!tip]- 标准解答
> **四次调用**依次为 Base 的 plain、Derived 的 kind、Derived 的 plain、Base 的 kind。
>
> **面试口述**
> 静态类型是编译时由声明与表达式确定的类型；这里通过 view 看到 Base 接口。动态类型描述它实际指向或引用的最派生对象类型，这里为 Derived。
>
> 普通非虚成员调用按静态查找和重载等规则确定；在本例中，view.plain 选择 Base 版本。虚函数调用在正常完整对象使用阶段选择相应的最终覆盖函数，所以 view.kind 调用 Derived 版本。显式 `Base::kind` 的限定调用抑制这次虚分派，直接调用指定的基类实现。
>
> **实现与保证分开**
> 常见实现使用虚函数表和对象中的相关指针，但标准规定的是行为，不规定这里必须有几张表、几个指针、固定多少字节。编译器也可能在可证明目标时消除间接调用。
>
> 本片段没有通过 Base 指针删除 Derived 对象；不要为了回答调用结果额外执行一个错误的删除版本。跨基类销毁的规则在第 5 题。
>
> **核对来源**：[N4659 · class.virtual](https://timsong-cpp.github.io/cppwp/n4659/class.virtual)、[expr.call](https://timsong-cpp.github.io/cppwp/n4659/expr.call)。

> [!info]- 深挖与追问
> **在基类构造函数中调用虚函数，会调用尚未构造完成的派生实现吗？**
> 对正在构造的那个对象，虚调用按当前构造阶段所属的类选择最终覆盖函数，不会像完整派生对象的普通使用阶段一样分派到更派生的覆盖。析构阶段也有相应限制。
>
> 这不是“virtual 失效”，而是构造 / 析构阶段的专门规则。不要在这些路径中对正在构造或销毁的对象虚调用纯虚函数；该错误具有未定义行为。
>
> **虚函数一定很慢吗？**
> 不能绝对判断。间接调用、内联机会、数据布局等可能影响性能，也可能发生去虚化；是否影响热路径必须按具体实现与工作负载测量。
>
> 来源：[N4659 · class.cdtor](https://timsong-cpp.github.io/cppwp/n4659/class.cdtor)、[class.abstract](https://timsong-cpp.github.io/cppwp/n4659/class.abstract)。

- [ ] 能根据静态类型、实际对象、virtual 与显式限定判断调用目标。

## CPP-OVERRIDE-001 · 同名函数为什么没有覆盖成功

> [!question] 问题 3 / 6 · 覆盖、重载与隐藏
> 下面是声明片段：
>
> ```cpp
> struct Rule {
>     virtual int apply(int value) const { return value; }
>     virtual ~Rule() = default;
> };
>
> struct AddOne : Rule {
>     int apply(int value) { return value + 1; }
> };
>
> AddOne concrete;
> const Rule& view = concrete;
> // view.apply(100)
> // concrete.apply(100)
> ```
>
> 两次调用各返回多少？为什么？如果只在 AddOne 的函数尾部加 `override` 会发生什么，正确修复是什么？
>
> 再区分 overload、override、name hiding；`using Rule::apply` 能不能让不匹配的签名自动变成覆盖？

学习入口：[[学习/2026-10-21/03-override与名字隐藏]]。

> [!hint]- 卡住时再看提示
> 检查函数名后面的完整声明，尤其是参数列表和成员函数末尾的 const。只看函数名相同不够。

> [!tip]- 标准解答
> 两次调用分别返回 **100、101**。派生类的 apply 缺少末尾 const，不覆盖基类的 const 虚函数；派生类同名声明还会影响名字查找。
>
> **修复声明：**
> ```cpp
> int apply(int value) const override {
>     return value + 1;
> }
> ```
>
> **面试口述**
> override 表达“我打算覆盖基类虚函数”，由编译器检查这个声明是否真的覆盖。原片段只加 override 而不补 const，会因没有覆盖相应基类函数而编译失败。
>
> overload 是让同名函数以不同参数列表参与重载选择；override 是派生函数覆盖基类虚函数；hiding 是派生作用域里的同名声明影响基类名字查找，即便参数不同也可能隐藏基类重载集合。三者不能混用。
>
> `using Base::f` 可把基类中的名字引入相应查找范围，帮助保留基类重载，不会把本来参数或 const 不匹配的函数变成覆盖。覆盖关系仍需满足语言规则。
>
> final 用在虚函数上阻止进一步覆盖，用在类上阻止继续派生。它不是“一定更快”或“自动防止所有切片”的保证。
>
> **核对来源**：[N4659 · class.virtual](https://timsong-cpp.github.io/cppwp/n4659/class.virtual)、[class.member.lookup](https://timsong-cpp.github.io/cppwp/n4659/class.member.lookup)、[namespace.udecl](https://timsong-cpp.github.io/cppwp/n4659/namespace.udecl)。

> [!info]- 深挖与追问
> **没有写 override，就一定不是覆盖吗？**
> 不一定。覆盖关系满足规则就存在，派生函数也继续是虚函数；override 提供显式意图和检查，不是产生覆盖关系的唯一方式。
>
> **返回类型只要不同就肯定不能覆盖吗？**
> 普通情况需要相同，但满足条件的类指针 / 引用返回类型允许协变；不能把这种例外推广成任意返回类型都能改变。初学先写清相同签名，协变规则按需再查。

- [ ] 能找出 const 错配，并区分覆盖、重载、隐藏的发生条件。

## CPP-ABSTRACT-001 · 抽象类怎样成为可替换接口

> [!question] 问题 4 / 6 · 接口与实现分离
> `virtual int apply(int value) const = 0;` 的 `= 0` 是在赋值吗？含有尚未提供非纯最终覆盖的纯虚函数的类，可以直接创建对象吗？可以有指针和引用吗？
>
> 抽象类能否有数据成员、构造函数、普通成员函数？为什么服务接收接口引用后，可以替换不同规则，而不把所有具体类型写进服务里？

学习入口：[[学习/2026-10-21/04-抽象类与接口]]。

> [!hint]- 卡住时再看提示
> 区分“不能直接创建一个完整的抽象对象”和“派生对象中不能构造基类部分”。再看调用方究竟需要知道接口能力，还是每种具体实现的类名。

> [!tip]- 标准解答
> **面试口述**
> 声明中的 `= 0` 是纯虚说明符，要求具体类为相应操作提供非纯的最终覆盖，否则它仍为抽象类。抽象类不能直接实例化为完整对象，但可以声明它的指针和引用，指向或引用具体派生对象。
>
> 抽象类可以有数据、构造函数和已有实现的普通成员。构造具体派生对象时，其抽象基类子对象仍要被初始化。C++ 中没有一个专门的 interface 关键字，常用抽象基类约定所需能力。
>
> 服务若只依赖这个能力接口，外部可提供不同实现。用引用传入表示借用；接口实现对象的存活必须覆盖服务的使用期。接口不必强制动态分配，具体实现也可以是作用域中的普通对象。
>
> **两个易错点**
> - 含有其他纯虚函数，不会自动把析构函数变成虚函数。若允许经基类拥有指针销毁对象，必须设计正确的析构接口。
> - 纯虚函数可以在类外提供定义；纯虚析构函数在相关对象被创建、需要析构时仍需有定义。不是在声明后直接写 `= 0 { ... }`。
>
> **核对来源**：[N4659 · class.abstract](https://timsong-cpp.github.io/cppwp/n4659/class.abstract)、[class.dtor](https://timsong-cpp.github.io/cppwp/n4659/class.dtor)。

> [!info]- 深挖与追问
> **继承接口与组合接口冲突吗？**
> 不冲突。具体规则可公有继承规则接口；使用规则的业务服务通过成员引用组合这个接口。前者表达可替换能力，后者表达依赖关系。
>
> **构造函数能声明 virtual 吗？**
> 不能。构造函数负责建立对象，它不使用普通虚成员那套 virtual 声明方式；析构函数则可以是虚函数。[N4659 · class.ctor](https://timsong-cpp.github.io/cppwp/n4659/class.ctor)。

- [ ] 能说明抽象接口怎么被使用、怎么被替换，以及借用对象的存活条件。

## CPP-VIRTUAL-DTOR-001 · 基类拥有指针怎样正确销毁派生对象

> [!question] 问题 5 / 6 · 多态销毁
> 一个由普通 `new Derived` 创建的非数组对象，若通过 `Base*` 执行普通 delete，在 C++17 下，Base 的析构需要满足什么条件？
>
> Base 只有其他虚成员、析构却不虚，能不能保证“仅执行 Base 析构，最多漏点内存”？把拥有者换成默认删除器的 `unique_ptr<Base>` 能自动修复吗？

学习入口：[[学习/2026-10-21/05-虚析构与基类销毁]]。

> [!hint]- 卡住时再看提示
> 普通 delete 使用什么静态类型？这个静态类型与实际对象的动态类型是否相同？智能指针最终采用哪种删除动作？

> [!tip]- 标准解答
> **面试口述**
> 对题目限定的普通非数组删除，若静态类型是实际派生类型的基类，那么该基类需要有虚析构，否则是未定义行为，不能预测成固定的“只析构 Base”。基类存在其他虚函数，并不会自动让它的析构变虚。
>
> 采用公有虚析构作为多态销毁接口时，正常析构过程会清理实际派生部分，再清理相应基类部分。`virtual ~Base() = default;` 是常用的默认实现形式。
>
> 默认删除器的 `unique_ptr<Base>` 最终同样需要正确的基类删除契约，不能修复非虚析构造成的错误。另一种工程设计是把不允许外部经基类销毁的基类析构设为 protected、非虚；这表达不同的接口约束。
>
> **核对来源**：[N4659 · expr.delete 第 3 段](https://timsong-cpp.github.io/cppwp/n4659/expr.delete#3)、[class.dtor](https://timsong-cpp.github.io/cppwp/n4659/class.dtor)、[unique.ptr.dltr.dflt](https://timsong-cpp.github.io/cppwp/n4659/unique.ptr.dltr.dflt)、[Core Guidelines C.35（工程建议）](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rc-dtor-virtual)。

> [!info]- 深挖：shared_ptr 的创建方式为什么影响删除
> `std::shared_ptr<Base> p = std::make_shared<Derived>();` 的共享管理状态保留了创建时销毁 Derived 所需的方式，不能等同于“最后直接对 Base* delete”。
>
> 但若先把 new Derived 的结果放进一个 Base*，再用该 Base* 构造采用默认删除动作的 shared_ptr，保存的删除类型已经不同；不能据此宣称所有 shared_ptr 写法都自动安全。
>
> 这个例外解释删除方式如何保存，不建议初学者靠偶然的创建路径绕开不清楚的多态接口设计。详解列出两种路径，错误版本不运行。
>
> 来源：[N4659 · shared_ptr 构造](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared.const)、[make_shared](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared.create)。

- [ ] 能判断基类删除契约，并且不会给未定义行为承诺固定输出。

## CPP-SLICE-001 · 为什么 virtual 也救不回按值保存的派生部分

> [!question] 问题 6 / 6 · 对象切片
> 假设 Base 是可复制的非抽象类，Derived 公有继承它，并覆盖 Base 的一个虚函数。执行 `Base saved = derived;` 后，saved 是什么类型的完整对象？
>
> 把多个 Derived 值放进 `vector<Base>`，为什么可能失去不同实现的行为？这一定是未定义行为吗？
>
> 比较按值接收 Base、借用 `const Base&`、持有 `vector<unique_ptr<Base>>` 三种接口的适用条件。

学习入口：[[学习/2026-10-21/06-对象切片与多态容器]]。

> [!hint]- 卡住时再看提示
> 是在原对象外面加了一层基类访问入口，还是已经创建了一份新的 Base 对象？virtual 选择的是哪个现存对象的覆盖函数？

> [!tip]- 标准解答
> **面试口述**
> `Base saved = derived` 创建的是新的 Base 完整对象，只复制用于初始化 Base 的部分，不把整个 Derived 类型塞进 Base 变量。这个现象称为对象切片；来源 Derived 仍是 Derived，新的 saved 已经是 Base。
>
> 正常可复制类型下，这种转换可以是合法程序，问题常是逻辑上丢失派生状态与行为，不应全部归为 UB。saved 后续虚调用只针对它自己这个 Base 对象，无法恢复没有保存在其中的派生部分。
>
> `vector<Base>` 的元素实际都是 Base 值，不能凭调用时加 virtual 自动保留不同派生类型。只在调用期间使用现有对象，可以借用 Base 引用；需要拥有不同派生对象时，可以用具有正确虚析构契约的基类拥有指针集合。
>
> `vector<unique_ptr<Base>>` 连续存的是管理对象，各个目标对象独立存放并保留实际类型；有分配与间接访问等代价。这里的新知识是保留派生类型，不是重讲昨天的 vector 扩容规则。
>
> **核对来源**：[N4659 · class.copy.ctor 的基类与成员复制规则](https://timsong-cpp.github.io/cppwp/n4659/class.copy.ctor)、[class.virtual](https://timsong-cpp.github.io/cppwp/n4659/class.virtual)、[Core Guidelines C.67（避免不受控多态复制的建议）](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#rc-copy-virtual)。

> [!info]- 深挖与追问
> **把 Base 的普通复制改成 std::move 就能避免切片吗？**
> 不能。目标仍是一个 Base 值时，不会因为来源表达式变成可移动类别，就神奇地把目标完整类型改成 Derived。
>
> **需要复制一份保留动态类型的多态对象怎么办？**
> 可以设计虚拟 clone 接口，由各具体类创建自己类型的副本，再以基类拥有指针返回。是否需要复制、异常保证与所有权都要另行约定；不是每个接口都必须支持复制。

## EX-20261021-001 · 修复一个丢失处理器类型的分发器

> [!question] 小练习 · 先分析，再写正确版本
> 下面是完整的安全程序，两个派生类各写了自己的处理方法，但输出不符合“加一 / 翻倍”的业务意图。
>
> ```cpp
> #include <iostream>
> #include <vector>
>
> struct PriceHandler {
>     int handle(int price) const { return price; }
> };
>
> struct AddOne : PriceHandler {
>     int handle(int price) const { return price + 1; }
> };
>
> struct DoublePrice : PriceHandler {
>     int handle(int price) const { return price * 2; }
> };
>
> int main() {
>     std::vector<PriceHandler> handlers;
>     handlers.push_back(AddOne{});
>     handlers.push_back(DoublePrice{});
>     for (const auto& handler : handlers) {
>         std::cout << handler.handle(100) << '\n';
>     }
> }
> ```
>
> 1. 解释现有程序输出，分别指出调用绑定与保存方式的问题。
> 2. 设计一个不能直接创建完整对象的公共接口，要求具体类实现 `handle`。
> 3. 让集合拥有两种实际处理器，能够逐个调用；保证通过接口销毁时正确。
> 4. 用编译器检查派生类签名，补上针对两种结果的断言。
>
> 算术只用于演示分发，price 取 100，不讨论整数溢出输入。

> [!hint]- 逐步提示
> 第一步确认容器元素的实际类型；第二步确认经公共接口调用的方法是否参与虚分派。最后再考虑拥有方式、删除契约与 override 检查。

> [!tip]- 参考答案与关键解释
> 原程序输出两行 100。handle 本来就不是虚函数；而且按值存到 vector<PriceHandler> 后，元素已是 PriceHandler，不再是完整的 AddOne / DoublePrice。
>
> 只给 handle 加 virtual 仍然无法修复已发生的切片；只换拥有指针却仍调用非虚方法，也无法按预期选择不同实现。两个问题都要处理。
>
> 接口和具体类的关键声明可以写成：
> ```cpp
> class PriceHandler {
> public:
>     virtual ~PriceHandler() = default;
>     virtual int handle(int price) const = 0;
> };
>
> class AddOne final : public PriceHandler {
> public:
>     int handle(int price) const override { return price + 1; }
> };
>
> class DoublePrice final : public PriceHandler {
> public:
>     int handle(int price) const override { return price * 2; }
> };
> ```
>
> 然后用 `std::vector<std::unique_ptr<PriceHandler>>` 管理两个具体对象，调用结果分别应为 101、200。虚析构保证基类拥有接口下的正确销毁；override 检查匹配的 const 签名；纯虚声明表达具体类必须提供行为。
>
> 完整逐行注释版：[[学习/2026-10-21/示例代码/07_dispatcher|在 Obsidian 中看源码]]。完整学习解释：[[学习/2026-10-21/06-对象切片与多态容器|切片与分发器详解]]。对应 `.cpp` 可单独编译运行。
>
> 来源：[N4659 · class.abstract](https://timsong-cpp.github.io/cppwp/n4659/class.abstract)、[class.virtual](https://timsong-cpp.github.io/cppwp/n4659/class.virtual)、[expr.delete](https://timsong-cpp.github.io/cppwp/n4659/expr.delete)。
