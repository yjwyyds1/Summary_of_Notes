## CPP-LIFE-001 · 栈、堆、存储期与生命周期

> [!question] 问题 1 / 6 · 基础概念
> 面试官问：“C++ 的栈和堆有什么区别？”你会怎样回答？
>
> 请进一步解释：局部 `std::vector<int>` 对象与它的元素存储是一回事吗？一个局部指针所指对象的生命周期，由这个指针的作用域决定吗？

学习详解：[[学习/2026-10-20/01-存储期与生命周期]]；读不懂指针语法先看 [[学习/2026-10-20/00-先读懂C++代码与对象|预备篇]]。

> [!hint]- 卡住时再看提示
> 分开考虑“变量/管理对象本身”和“它管理的资源”。再区分语言规定的存储期与机器上常见的实现方式。

> [!tip]- 点击查看标准解答
> **面试口述（约 60–90 秒）**
>
> C++ 标准规定的是自动、静态、线程和动态四类存储期。日常所说的“栈对象”通常指自动存储期对象，“堆对象”通常指动态分配对象，但物理栈、堆属于实现层面，不能和标准分类完全画等号。
>
> 自动对象通常随所在作用域退出而销毁；动态对象通常需要由所有者通过 `delete`、智能指针或其他资源管理机制结束生命周期。局部裸指针变量消失，不会自动删除它指向的动态对象。局部 `vector` 的管理对象可以是自动存储期，它用默认分配器取得的元素存储却是动态分配的。
>
> **常见分类**
>
> | 存储期 | 典型例子 | 理解重点 |
> | --- | --- | --- |
> | 自动 | 普通局部变量 | 常见实现放在栈或寄存器，也可能被优化掉 |
> | 静态 | 全局变量、局部 `static` | 存储贯穿程序；对象初始化/析构另有规则 |
> | 线程 | `thread_local` 变量 | 每线程有独立实体，已构造对象在线程退出时析构 |
> | 动态 | 普通 `new` 创建的对象 | 由资源所有权与释放操作管理 |
>
> ```cpp
> #include <cassert>
> #include <memory>
> #include <vector>
>
> int main() {
>     auto owner = std::make_unique<int>(42);
>     int* observer = owner.get();
>     std::vector<int> values{1, 2, 3};
>     assert(*observer == 42);
>     assert(values.size() == 3);
> } // values、owner 析构；各自管理的资源被释放
> ```
>
> 这里 `owner`、`observer`、`values` 都是自动对象；`observer` 只观察，不拥有；`owner` 管理的 `int` 与 `values` 管理的元素存储要另算。
>
> **易错点**
> - 存储期回答“存储可以持续多久”，对象生命周期回答“对象何时存在”；两者有关，但不是同一概念。按本篇 C++17 草案，对具有非空初始化（non-vacuous initialization）的普通类对象，取得合适存储并完成初始化才开始生命周期；对有非平凡析构函数的类对象，析构调用开始会结束其生命周期。释放或特定重用存储也能结束生命周期。析构与释放存储仍是不同步骤。
> - “栈一定快、堆一定慢”过于绝对。动态分配可能涉及分配器、同步、缺页等成本，但实际差异依赖实现、分配模式与测量条件。
>
> **核对来源**：[N4659 · basic.stc：四类存储期](https://timsong-cpp.github.io/cppwp/n4659/basic.stc)、[basic.life：生命周期与存储的区别](https://timsong-cpp.github.io/cppwp/n4659/basic.life)。

> [!info]- 深挖与追问（选学）
> **追问：内存池已经拿到一大块内存，里面的对象就都存在了吗？**
>
> 不一定。对需要显式构造的类型，可以先分配原始存储，再用 placement new 在指定位置构造对象，最后分别析构与归还存储。不能仅凭“这块地址可访问”就调用尚未构造对象的成员。
>
> **追问：为什么行情模块返回局部对象的地址会出问题？**
>
> 返回后该局部对象已结束生命周期，调用者再解引用会产生未定义行为。换成引用返回也不会自动延长它的生命周期；应明确返回值、所有权或由调用方提供存储。
>
> **边界**：不要把上述概括推广到所有临时对象、联合体、隐式对象创建规则；这些需要按类型、语法和标准版本单独判断。首日先掌握管理对象与被管理资源的区别。

## CPP-RAII-001 · RAII 为什么能防止资源泄漏

> [!question] 问题 2 / 6 · 资源管理
> 什么是 RAII？它为什么能处理提前 `return` 和异常路径？
>
> 如果函数中已经打开文件、获取互斥锁，之后一步抛异常，怎样避免遗漏清理？RAII 能保证进程被强制终止时也执行清理吗？

学习详解：[[学习/2026-10-20/02-RAII与异常清理]]。

> [!hint]- 卡住时再看提示
> 想一想：清理动作应该散落在每条退出路径里，还是交给一个拥有资源的对象？正常作用域退出和异常栈展开分别会发生什么？

> [!tip]- 点击查看标准解答
> **面试口述（约 60 秒）**
>
> RAII 是把资源的所有权绑定到对象生命周期：构造时取得或接管资源，析构时释放。资源可以是内存，也可以是锁、文件描述符或连接。使用作用域内的资源管理对象后，正常退出、提前返回，以及异常向处理器传播时的栈展开，都可以触发已构造对象的析构，减少遗漏清理的可能。
>
> 例如使用 `unique_ptr` 管理动态对象、`lock_guard` 管理锁。RAII 解决资源释放配对，不自动保证业务操作回滚，也不保证强制终止进程时还会执行析构。
>
> ```cpp
> #include <cassert>
> #include <memory>
> #include <stdexcept>
>
> struct Resource {
>     int& live;
>     explicit Resource(int& n) : live(n) { ++live; }
>     ~Resource() noexcept { --live; }
> };
>
> void work(int& live) {
>     auto resource = std::make_unique<Resource>(live);
>     throw std::runtime_error("work failed");
> }
>
> int main() {
>     int live = 0;
>     try { work(live); }
>     catch (const std::runtime_error&) {}
>     assert(live == 0);
> }
> ```
>
> **关键边界**
> - 向匹配异常处理器传播时，已完成构造、尚未析构的自动对象按构造完成的逆序销毁。
> - 普通非委托构造函数抛异常时，完整对象尚未构造成功，它自身的析构函数不会执行；已经构造完成的成员和基类会清理。因此资源应尽早交给 RAII 成员，避免在构造函数里先裸分配再做可能抛异常的操作。
> - 析构/资源释放不应让异常逃出。栈展开期间析构再抛异常并向外传播，会触发 `std::terminate`。
> - `abort`、强制杀进程等不能依赖自动对象析构；未捕获异常、违反 `noexcept` 等也不能一概承诺完整展开。
>
> **核对来源**：[N4659 · except.ctor：栈展开与构造失败](https://timsong-cpp.github.io/cppwp/n4659/except.ctor)、[except.terminate：终止情形](https://timsong-cpp.github.io/cppwp/n4659/except.terminate)、[Core Guidelines R.1：RAII 工程建议](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-raii)。

> [!info]- 深挖与追问（选学）
> **追问：RAII 和异常安全是一个意思吗？**
>
> 不是。RAII 常帮助实现“资源不泄漏”，但操作执行一半后，业务状态可能已改变。基本保证关注对象不变量与无泄漏；强保证要求失败后状态不变；不抛保证要求操作不抛异常。需要分别设计。
>
> **追问：每个管理资源的类都要手写析构、复制、移动吗？**
>
> 尽量让成员类型（如 `vector`、`unique_ptr`）管理资源，使用编译器生成的适当操作，即 Rule of Zero。直接拥有裸资源且手写特殊成员时，再系统考虑复制/移动语义，不能只补一个析构就结束。
>
> **交易场景**：行情解析失败时释放临时缓冲区、订单处理退出时解锁，适合用 RAII。磁盘写入是否持久化、订单是否已经发出，则仍需额外业务协议。
>
> 参考：[Core Guidelines C.20：避免不必要的手写特殊成员](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rc-zero)。

## CPP-OWN-001 · 三种智能指针如何选择

> [!question] 问题 3 / 6 · 所有权
> `unique_ptr`、`shared_ptr`、`weak_ptr` 分别解决什么问题？
>
> 一个行情对象由单个模块负责销毁，另一个模块只临时读取，你会怎么设计？为什么不能为了“保险”把所有指针都改成 `shared_ptr`？

学习详解：[[学习/2026-10-20/03-所有权与智能指针]]。

> [!hint]- 卡住时再看提示
> 先回答“谁有责任维持对象存活”，再选择工具。观察对象和拥有对象是两种不同职责。

> [!tip]- 点击查看标准解答
> **面试口述（约 60–90 秒）**
>
> `unique_ptr` 表达独占所有权，不能复制，可通过移动把所有权交给另一个管理者。`shared_ptr` 表达共享所有权，最后一个强拥有者离开后触发相应删除操作。`weak_ptr` 是配合共享所有权使用的弱观察者，不保持对象存活，使用前通过 `lock()` 尝试取得临时强引用。
>
> 只有一个所有者时优先考虑直接值成员或 `unique_ptr`；确实需要多个独立使用者共同维持生命周期时才选择 `shared_ptr`。只在调用期间借用对象可传 `T&`/`const T&`，允许空值时可传观察用 `T*`，前提是保证使用期间对象仍存活。
>
> | 工具 | 拥有资源 | 复制 / 转移 | 常见用途 |
> | --- | --- | --- | --- |
> | `unique_ptr<T>` | 独占 | 不可复制，可移动 | 单所有者、工厂返回对象 |
> | `shared_ptr<T>` | 共享 | 可复制，共享管理状态 | 独立使用者需要共同延长存活期 |
> | `weak_ptr<T>` | 不维持对象存活 | 可复制，`lock()` 获取强引用 | 非拥有关系、打破强引用环 |
> | `T*` / `T&` | 类型本身不表达拥有权 | 不自动释放资源 | 约定明确的短期借用 |
>
> **为什么不全部使用 shared_ptr？**
>
> 它引入共享管理状态、引用计数更新与生命周期推理成本；常见实现的计数同步也有开销。真正的所有者可能变得不清楚，强引用环还可能泄漏。它不会自动把业务对象变成线程安全对象。
>
> **循环引用与安全读取**
>
> ```cpp
> #include <cassert>
> #include <memory>
>
> struct Node {
>     std::shared_ptr<Node> next;
>     std::weak_ptr<Node> prev; // 回边是观察关系
> };
>
> int main() {
>     auto a = std::make_shared<Node>();
>     auto b = std::make_shared<Node>();
>     a->next = b;
>     b->prev = a;
>     if (auto parent = b->prev.lock()) {
>         assert(parent.get() == a.get());
>     }
> }
> ```
>
> 如果这里把 `prev` 也做成 `shared_ptr`，`a` 与 `b` 会形成强引用环。应按真实所有权选一条非拥有关系，不能机械地把所有边都改弱引用。
>
> **核对来源**：[N4659 · unique.ptr](https://timsong-cpp.github.io/cppwp/n4659/unique.ptr)、[util.smartptr.shared](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared)、[weak_ptr::lock](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.weak.obs)。独占优先与弱引用打破环是 [Core Guidelines R.21/R.24 的工程建议](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-unique)。

> [!info]- 深挖与追问（选学）
> **追问：先判断 `!w.expired()`，再使用原始指针可以吗？**
>
> 不够。检查之后对象可能被其他线程释放。用 `if (auto p = w.lock())` 原子地尝试获得强拥有者；成功后由 `p` 维持对象存活。注意它仍不保护对象内部数据的并发访问。
>
> **追问：`make_shared` 一定更省内存，而且最后一个 shared_ptr 消失就立即归还整块存储吗？**
>
> 常见实现把控制块与对象合并分配，C++17 草案鼓励不多于一次分配，但不是强制所有实现都如此。合并分配时，最后一个强引用消失会销毁对象；若仍有弱引用，包含控制块的整块分配可能保留到弱引用也消失。**对象已析构**和**存储尚保留**必须分开。
>
> **追问：函数参数何时应传智能指针？**
>
> 需要表达接管或保留所有权时再用。例如按值接收 `unique_ptr<T>` 表示接管所有权；按值接收 `shared_ptr<T>` 可保留一份共享拥有权。仅访问对象的同步函数常可接收引用，借用有效期由接口约定保证。
>
> 参考：[N4659 · shared_ptr 创建函数](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared.create)、[微软 STL 关于 shared_ptr 分配布局的解释](https://devblogs.microsoft.com/oldnewthing/20230815-00/?p=108602)、[Core Guidelines R.30/R.32](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rr-smartptrparam)。

## CPP-SHARED-001 · shared_ptr 的线程安全边界

> [!question] 问题 4 / 6 · 并发基础
> “`shared_ptr` 的引用计数是线程安全的，所以 `shared_ptr` 以及它指向的对象都可以随便跨线程使用。”这句话哪里有问题？
>
> 请区分：两个不同的 `shared_ptr` 实例、同一个 `shared_ptr` 实例、它们指向的业务对象。

学习详解：[[学习/2026-10-20/04-shared_ptr与线程安全]]。

> [!hint]- 卡住时再看提示
> 画三层：管理状态、指针变量本身、业务数据。安全保证究竟落在哪一层？

> [!tip]- 点击查看标准解答
> **面试口述（约 60–90 秒）**
>
> 要分三层。第一，已经各自持有的不同 `shared_ptr` 实例即使共享所有权，也可以分别并发复制、销毁或 `reset`，相关共享管理状态由实现保证安全。第二，同一个 `shared_ptr` 实例如果一边读取或复制，另一边同时 `reset` 或赋值，需要同步。第三，指向的 `T` 没有因此得到保护，对 `T` 的并发读写还要靠锁、原子或其他正确同步机制。
>
> 因而引用计数安全只解决部分生命周期管理问题，不等于业务数据安全，也不等于对象已被正确发布给其他线程。
>
> | 场景 | 结论与前提 |
> | --- | --- |
> | 线程 A 操作 `a`，线程 B 操作 `b`，二者是已正确发布的不同 shared_ptr 实例 | 各自复制/释放共享所有权可以并发 |
> | A 执行 `p.reset()`，B 同时从同一个 `p` 复制 | 普通访问需要同步，否则可能数据竞争 |
> | `a` 与 `b` 指向同一个普通 `int`，两个线程都执行 `++*a` / `++*b` | 没有额外同步则发生数据竞争，属于 UB |
> | 多线程只读取已经正确初始化、发布且不再修改的对象 | 可以只读共享；发布和存活前提仍要满足 |
>
> **如何处理同一个指针变量的发布/替换？**
>
> C++17 可以用互斥锁，或专门面向 `shared_ptr` 的 `std::atomic_load`、`std::atomic_store` 等自由函数；并发访问该指针变量时要统一使用相应同步方式。C++20 才引入 `std::atomic<std::shared_ptr<T>>` 特化。
>
> 即使原子替换了指针，拿到的业务对象若仍会被修改，其数据访问仍须另行同步。
>
> **核对来源**：[N4659 · shared_ptr 的数据竞争规则](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared#4)、[C++17 的 shared_ptr 原子访问接口](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared.atomic)、[微软标准库线程安全说明](https://learn.microsoft.com/en-us/cpp/standard-library/thread-safety-in-the-cpp-standard-library?view=msvc-170)。

> [!info]- 深挖与追问（选学）
> **追问：`use_count() == 1` 可以当成“我独占访问，可以免锁修改”的依据吗？**
>
> 不能。它只观察拥有者数量，不建立对业务数据的同步关系；原始指针/引用可能仍在使用对象，其他线程也可能从弱引用取得拥有权。不要把计数查询当作并发协议。
>
> **追问：低延迟交易系统是不是应该禁用 shared_ptr？**
>
> 不应一概而论。高频复制/销毁可能带来计数同步、缓存争用，最后一个拥有者释放时还可能触发复杂析构或分配器工作。但是否处于关键路径、是否真的需要共享所有权、能否用阶段所有权或消息转移替代，需要结合正确性和测量判断。
>
> **追问：用 `shared_ptr<const Snapshot>` 发布快照就一定安全了吗？**
>
> 还要保证发布指针的同步，并避免其他可写别名修改同一个对象，以及对象内部隐藏的可变状态产生竞争。`const` 指针不能替代完整的并发协议。
>
> 参考：[N4659 · use_count 的备注](https://timsong-cpp.github.io/cppwp/n4659/util.smartptr.shared.obs)。

## CPP-MOVE-001 · 移动语义与值类别

> [!question] 问题 5 / 6 · 移动语义
> `std::move(x)` 会把 `x` 的资源“搬走”并清空它吗？为什么 `T&& x` 中使用名字 `x` 时还可能发生复制？
>
> 再解释：对 `const std::string` 使用 `std::move` 会发生什么？一个对象被移动后还能做哪些操作？

学习详解：[[学习/2026-10-20/05-复制移动与值类别]]。

> [!hint]- 卡住时再看提示
> 把“把表达式转换成什么类别”与“最终调用哪个构造/赋值函数”分开。再留意 `const` 是否被去掉。

> [!tip]- 点击查看标准解答
> **面试口述（约 60–90 秒）**
>
> `std::move` 本身只是转换，通常把表达式转成将亡值 xvalue，使后续重载决议有机会选择移动操作；它不调用移动构造，也不保证发生资源转移。真正的行为取决于选中的构造/赋值函数。
>
> 命名的右值引用变量，其名字表达式仍是左值；需要再次转成右值表达式，才可能选择移动重载。`std::move` 保留 `const`，所以对 `const std::string` 移动构造普通 `string` 时，常规 `string(string&&)` 无法绑定，最终会选择复制构造。对其他类型要看具体重载，也可能编译失败。
>
> **一个能实际验证的例子**
>
> ```cpp
> #include <cassert>
> #include <memory>
> #include <type_traits>
> #include <utility>
>
> int main() {
>     auto p = std::make_unique<int>(42);
>     auto&& r = std::move(p); // 绑定引用，没有构造另一个 unique_ptr
>     assert(p != nullptr);
>     static_assert(std::is_lvalue_reference_v<decltype((r))>);
>     // auto bad = r;         // 复制 unique_ptr，不允许
>     auto q = std::move(r);  // 此处才调用移动构造
>     assert(p == nullptr);
>     assert(*q == 42);
> }
> ```
>
> **移动后状态不能一概说“清空”**
>
> - 对标准库类型，除非另有更强约定，移动后保证有效但状态未指定：可以析构；类型本身支持赋值时也可以重新赋值。调用其他操作仍要满足其前置条件。例如对移后容器调用 `front()` 前必须先确认非空。
> - `unique_ptr` 向另一个对象成功移动后，源明确为空，是更强保证。
> - 移后 `std::string` 不保证一定为空；不能依赖某一次实验观察到的内容。
> - 任意自定义类型的移动后状态要看它的实现/契约，不能机械套用所有标准库类型的约定。
>
> **核对来源**：[N4659 · forward：move 的返回转换](https://timsong-cpp.github.io/cppwp/n4659/forward)、[expr：命名右值引用表达式](https://timsong-cpp.github.io/cppwp/n4659/expr#7)、[标准库移后状态](https://timsong-cpp.github.io/cppwp/n4659/lib.types.movedfrom)、[unique_ptr 移动后源为空的保证](https://timsong-cpp.github.io/cppwp/n4659/unique.ptr#4)。

> [!info]- 深挖与追问（选学）
> **追问：移动一定比复制便宜吗？**
>
> 不一定。转移动态缓冲区通常便宜，但小对象、短字符串优化、自定义移动逻辑等会影响成本。移动是语义能力，不是性能承诺。
>
> **追问：为什么移动构造常写 `noexcept`？**
>
> 它表明移动不抛异常，有助于容器在搬迁元素时兼顾异常保证。常见 `vector` 实现对可复制且移动可能抛异常的类型，会考虑复制旧元素；不能简化成“有移动构造就一定移动”，也不能反过来说“非 noexcept 就一定复制”，还要看类型能力和具体操作。
>
> **追问：是不是 `return std::move(local);` 总比 `return local;` 快？**
>
> 不是。满足条件时应允许返回值优化/隐式移动；显式 `std::move` 可能阻止 NRVO。C++17 对特定纯右值返回有保证的消除规则，NRVO 本身仍非普遍强制。该专题后续可单独展开。
>
> 参考：[N4659 · vector 的异常与搬迁相关条件](https://timsong-cpp.github.io/cppwp/n4659/vector.modifiers)、[class.copy.elision](https://timsong-cpp.github.io/cppwp/n4659/class.copy.elision)。

## STL-VECTOR-001 · reserve、resize 与引用失效

> [!question] 问题 6 / 6 · 容器与内存
> `vector` 的 `size()` 和 `capacity()` 有什么区别？`reserve(n)` 与 `resize(n)` 各改变什么？
>
> 缓存了元素的指针、引用或迭代器之后再 `push_back`，什么时候安全？如果没有扩容，之前保存的 `end()` 还能用吗？

学习详解：[[学习/2026-10-20/06-vector与综合练习]]。

> [!hint]- 卡住时再看提示
> 分清“已经存在的元素”和“无需重新分配时能容纳多少元素”。追加时是否重新分配，是判断已有元素地址的关键。

> [!tip]- 点击查看标准解答
> **面试口述（约 60–90 秒）**
>
> `size()` 是当前元素数量，`capacity()` 是现有存储不重新分配时可容纳的元素数量。`reserve(n)` 请求容量至少达到 `n`，不改变 `size()`，也不在剩余容量中创建额外元素；`resize(n)` 则实际增加或删除元素，必要时可能重新分配。
>
> `vector` 重新分配会使原来指向其元素的指针、引用、迭代器以及旧 `end()` 失效。尾部追加如果没有重新分配，原有元素的指针、引用和迭代器保持有效，但旧 `end()` 仍失效。因此不能把“未扩容”说成“所有迭代器都有效”。
>
> **操作速查**
>
> | 操作 | size 是否改变 | 对已有元素/引用的影响 |
> | --- | --- | --- |
> | `reserve(n)`，`n <= capacity()` | 不变 | 不重新分配，原引用保持有效 |
> | `reserve(n)`，`n > capacity()` | 不变 | 重新分配，原元素引用全部失效 |
> | `resize(n)`，`n > size()` | 增大 | 构造新增元素；未重新分配时原元素引用有效，旧 end 失效；重新分配则全部失效 |
> | `resize(n)`，`n < size()` | 减小 | 尾部元素被销毁，保留元素引用有效，旧 end 失效 |
> | `push_back` 未重新分配 | 增大 | 原元素引用有效，旧 end 失效 |
> | `push_back` 重新分配 | 增大 | 原元素相关引用全部失效 |
>
> ```cpp
> #include <cassert>
> #include <vector>
>
> int main() {
>     std::vector<int> v;
>     v.reserve(8);
>     assert(v.size() == 0);
>     assert(v.capacity() >= 8);
>     // v[0] = 7; // 错误：尚无元素，不属于有效下标
>     v.resize(3);
>     assert(v.size() == 3);
>     assert(v[0] == 0); // 此处为默认分配器下新增的 int
> }
> ```
>
> **易错点**
> - `reserve` 不改变 size，不意味着它完全不调用构造函数：重新分配时可能要移动/复制已有元素。
> - `resize` 不等于“给任意类型清零”。它按类型和分配器构造新增元素；`vector<int>` 默认分配器的这个例子才可得到零值。
> - `push_back` 通常说摊还 O(1)，但某一次重新分配需要 O(n) 搬迁工作，不能据此保证单次低延迟。
> - 容量增长倍数没有统一的标准保证；`shrink_to_fit()` 也是非强制请求。
>
> **核对来源**：[N4659 · vector.capacity：reserve/resize/shrink_to_fit](https://timsong-cpp.github.io/cppwp/n4659/vector.capacity)、[vector.modifiers：追加、插入、删除和失效](https://timsong-cpp.github.io/cppwp/n4659/vector.modifiers)、[vector.overview：摊还复杂度](https://timsong-cpp.github.io/cppwp/n4659/vector.overview)。

> [!info]- 深挖与追问（选学）
> **追问：容量足够时，往中间插入就完全不影响引用吗？**
>
> 仍会影响插入位置及其之后的元素引用/迭代器，插入点之前的保持有效。`erase` 也会使删除位置及其之后的迭代器/引用失效。上面的“保留原元素引用”仅针对没有重新分配的尾部追加。
>
> **追问：`emplace_back` 一定比 `push_back` 快吗？**
>
> 不是。`emplace_back(args...)` 用转发后的参数直接在元素位置构造，某些场景可避免先造临时对象；传入一个现成的 `T` 时二者可能都复制或移动。它也不能消除重新分配时已有元素的搬迁。应按参数形态与实际测量判断。
>
> **追问：低延迟行情缓存为什么会提前 reserve？**
>
> 合理预留容量可减少热路径重新分配与搬迁，但会增加内存占用，且不保证绝不超过预估上限。要结合容量上限、溢出策略与延迟分布设计；不能靠每次追加前 `reserve(size()+1)` 破坏正常摊还增长。
>
> **边界**：上述普通连续元素讨论以 `vector<T>` 的常规类型为主，`vector<bool>` 是特殊化，不能直接套用普通 `T*`/`T&` 的全部模型。

## EX-20261020-001 · 行情缓存中的悬垂指针

> [!question] 小练习 · 先独立判断，再看答案
> 以下代码按 C++17、单线程、分配成功考虑。A、B 两处各有什么问题？能否给出固定输出？
>
> 再想两种修正方法：如果缓存必须连续存放行情值，怎么办？如果业务必须长期持有对象地址，又怎么办？
>
> ```cpp
> #include <iostream>
> #include <vector>
>
> int main() {
>     std::vector<int> prices;
>     prices.reserve(2);
>     // A: prices[0] = 100;
>     prices.push_back(100);
>     int* best = &prices[0];
>     const auto old_capacity = prices.capacity();
>     prices.reserve(old_capacity + 1);
>     // B: std::cout << *best << '\n';
> }
> ```
>
> A、B 故意注释，**请分析取消对应注释的后果**。不需要运行带有 UB 的版本来“看结果”。

学习详解：[[学习/2026-10-20/06-vector与综合练习|两种修正方法、对象地址图与代码]]。

> [!hint]- 卡住时再看提示
> 第一处检查 size，第二处检查地址是否还属于原来的元素对象。这里第二次 reserve 的参数刻意大于旧 capacity。

> [!tip]- 点击查看参考答案与修正
> **A：越界访问。** 第一次 `reserve(2)` 后 size 仍为 0，没有第 0 个元素，不能赋值给 `prices[0]`。应通过 `push_back` 添加，或先 `resize` 再合法下标访问。
>
> **B：悬垂指针解引用。** 第二次 `reserve` 请求的容量大于旧容量，成功时必然重新分配；原元素指针 `best` 失效。取消 B 的注释后解引用具有未定义行为，不能承诺打印旧值、随机数或一定崩溃。
>
> **修正一：连续存值，跨重新分配只保存索引，需要时重新取引用。**
>
> ```cpp
> #include <cassert>
> #include <vector>
>
> int main() {
>     std::vector<int> prices;
>     prices.reserve(2);
>     prices.push_back(100);
>     const auto best_index = prices.size() - 1;
>     prices.reserve(prices.capacity() + 1);
>     assert(prices[best_index] == 100);
> }
> ```
>
> 本例只重新分配而没有插入/删除已有元素，索引仍指向同一逻辑元素。若排序、中间插入或删除会改变位置，索引也可能逻辑失效，应考虑稳定 ID 或句柄，并管理删除后的有效性。
>
> **修正二：对象由独立的 unique_ptr 拥有，vector 只搬迁这些管理者。**
>
> ```cpp
> #include <cassert>
> #include <memory>
> #include <vector>
>
> int main() {
>     std::vector<std::unique_ptr<int>> prices;
>     prices.push_back(std::make_unique<int>(100));
>     int* best = prices[0].get();
>     prices.reserve(prices.capacity() + 1);
>     assert(*best == 100);
> }
> ```
>
> 重新分配会搬迁 `unique_ptr` 管理对象，但被它拥有的独立 `int` 不随之搬迁。`best` 在对应拥有者没有删除/重置该对象时有效。代价是通常多一层间接访问、独立分配及不同的局部性特征；这只是生命周期设计示范，不代表最佳行情缓存方案。
>
> **能不能只在开头 reserve 一个大数解决？**
>
> 只有明确保证后续操作不再触发重新分配、删除或相关位置变动时，才可以依赖相应稳定性。预估容量不是生命周期契约。也不能靠改成 `shared_ptr` 来修复任意裸指针的失效。
>
> **核对来源**：[N4659 · reserve 引用失效规则](https://timsong-cpp.github.io/cppwp/n4659/vector.capacity)、[unique_ptr 移动构造与被管理指针](https://timsong-cpp.github.io/cppwp/n4659/unique.ptr.single.ctor)。
