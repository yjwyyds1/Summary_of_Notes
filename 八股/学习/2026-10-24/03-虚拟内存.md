# 03 · 为什么进程看到的是虚拟地址

← [[学习/学习导航/2026-10-24-学习导航|学习导航]] · [[八股测试/2026-10-24#OS-VM-001 · 为什么需要虚拟内存|自测题]] · [[学习/2026-10-24/示例代码/03_virtual_memory|代码阅读版]]

程序里的指针数值通常是**虚拟地址**，不是直接写在内存条上的“物理地址”。操作系统与硬件通过页表维护虚拟页到物理页框的映射。**页**是固定大小的虚拟内存块；**页框**是物理内存里的对应大小块。地址拆成“页号 + 页内偏移”，翻译时换页号，偏移不变。不同进程因此能拥有各自的地址空间、访问权限，也可受控共享与按需分配。

```mermaid
flowchart LR
  V["虚拟地址 0x1234"] --> A["4 KiB 页：页号 1，偏移 0x234"]
  A --> T["示意页表：页 1 → 页框 7"]
  T --> R["示意物理地址 0x7234"]
```

这只是**教学模型**：真实系统可能有多级页表、不同页大小、缓存翻译结果的 TLB、文件映射等。TLB 是处理器缓存近期地址翻译结果的结构，不能说“每次访问都完整走一遍页表”。缺少当前有效映射时会触发**缺页异常**；操作系统判断是可补入的合法页，还是非法访问。缺页异常不等于必然崩溃。虚拟空间大不代表已占用同样多物理内存；虚拟地址连续也不保证物理页连续。

## 从一个地址走到物理内存

程序说“读取地址 `0x1234`”，CPU 实际需要知道这个虚拟地址对应哪块物理内存。假设本例页大小是 4096 字节，也就是 `0x1000`，那么 `0x1234` 可拆成虚拟页号 1 和页内偏移 `0x234`。若示意页表登记“虚拟页 1 → 物理页框 7”，物理地址就是 `0x7000 + 0x234 = 0x7234`。翻译改的是页所在位置，页内偏移保持不变。这个算式先帮助你读懂页和页框，不是说真实系统只用一张 `unordered_map` 页表。

为什么要多这一层？两个进程都可以使用看起来相同的虚拟地址，却映射到不同物理页，互不改写；操作系统也可以让它们明确共享某些映射。页表项还带访问权限，读、写、执行并非随意允许。虚拟地址连续不要求物理页连续，申请了大片虚拟范围也不等于已经占满同样多的物理内存。[Linux mmap(2)](https://man7.org/linux/man-pages/man2/mmap.2.html) 可帮助理解映射由操作系统建立。

**TLB** 可以先理解为地址翻译结果的小缓存：命中时不必每次都完整查询页表。**缺页异常**是访问时发现当前映射需要内核处理的事件，不等于“程序必崩”；合法的按需分配或文件映射可以由内核补齐，非法地址或权限错误则不能当作正常数据使用。代码中 `find` 失败只能说明我们的教学映射表没有条目，不能直接等同于某次真实缺页的全部处理过程。

## 用算术模型读懂翻译

下面的 `page_table` 只是普通 C++ `unordered_map`（键到值的映射容器），没有读系统真实页表。4 KiB = 4096 字节，`0x1234 / 4096 = 1`，余数 `0x234`；映射页 1 → 页框 7 后得到 `7*4096+0x234 = 0x7234`。

```cpp
// C++17 算术模型：把虚拟地址拆成“虚拟页号 + 页内偏移”，再查示意页表。
// 这不是操作系统页表，也不读取真实物理地址；页大小 4096 只是本题给定值。
#include <cassert>       // assert：核对算式。
#include <cstdint>       // uint64_t：明确使用非负整数表示示意地址。
#include <iostream>      // cout：显示翻译结果。
#include <unordered_map> // unordered_map：保存“虚拟页号 -> 物理页框号”的示意映射。

int main() {
    constexpr std::uint64_t page_size = 4096; // 本例约定 4 KiB 页。
    constexpr std::uint64_t virtual_address = 0x1234;
    const std::uint64_t virtual_page = virtual_address / page_size; // 高位选页。
    const std::uint64_t offset = virtual_address % page_size;       // 低位页内偏移。
    // 虚拟第 1 页映到物理第 7 页；真实操作系统有权限位和多级页表等更多信息。
    const std::unordered_map<std::uint64_t, std::uint64_t> page_table{{1, 7}};
    const auto found = page_table.find(virtual_page); // 不存在时不能解引用 end()。
    assert(found != page_table.end());
    const std::uint64_t physical_address = found->second * page_size + offset;
    assert(virtual_page == 1 && offset == 0x234 && physical_address == 0x7234);
    std::cout << "virtual page=" << virtual_page << " offset=" << offset
              << " -> model physical address=0x" << std::hex << physical_address << '\n';
}
```

**作用与场景**：两个进程即使打印同一虚拟地址数值，也不能据此认为指向同一物理位置；共享内存由操作系统建立共同映射。进程隔离、权限保护、文件映射与按需载入都利用映射。它与 C++ 对象“自动/静态/动态存储期”是不同维度。

## 把地址翻译当作两步算术

第一步先定位虚拟页：`0x1234` 在大小为 `0x1000` 的页中，可写成 `1×0x1000+0x234`。因此页号是 1，偏移是 `0x234`。第二步查示意映射：页 1 对应页框 7，把前面的 1 换成 7，得到 `7×0x1000+0x234=0x7234`。代码用整数除法和取余完成第一步，用 `unordered_map::find` 完成第二步。`find` 结果等于 `end()` 时不能解引用；示例用 `assert` 说明“此页已映射”是预设条件。

真实系统不能把指针转成整数后照这个表自己求物理地址。页表由操作系统和硬件管理，访问还要检查权限；TLB 可能直接提供近期翻译结果。缺页时内核也不是简单地给 `unordered_map` 添一项：它可能分配物理页、读入文件内容，或判定访问非法。初学时把“地址翻译”“数据实际存放”“C++ 对象是否还活着”分成三个问题。例如 `delete` 后继续使用指针，即使某个虚拟页仍映射，也不代表该对象仍有效。

再想共享内存：进程 A 的某虚拟页和进程 B 的另一虚拟页可以被安排到同一物理页框，因此它们能够交换数据；虚拟地址数值不必相同。反过来，两进程即使碰巧打印相同地址，也可能指向不同页框。这正是不能凭指针数值推断跨进程共享的原因。

**面试口述**：进程使用虚拟地址，页表把虚拟页映到物理页框并检查权限；从而隔离地址空间、允许受控共享与按需映射。未映射访问可能触发合法缺页处理，也可能是非法访问。
