# 04 · 两把锁为什么会卡住

← [[学习/学习导航/2026-10-24-学习导航|学习导航]] · [[八股测试/2026-10-24#CON-DEADLOCK-001 · 什么是死锁，怎样避免|自测题]] · [[学习/2026-10-24/示例代码/04_deadlock|代码阅读版]]

**互斥锁**像同一时刻只给一人用的钥匙。线程 A 拿着锁 X 等 Y，线程 B 拿着 Y 等 X，两人都不放手，就出现等待环，程序无法继续。更长的多资源环也可能发生。

```mermaid
flowchart LR
  A["线程 A 已拿 X"] --> W1["等待 Y"]
  W1 --> B["线程 B 已拿 Y"]
  B --> W2["等待 X"]
  W2 --> A
```

经典四个必要条件是：**互斥**（资源不能同时被多人占用）、**占有并等待**（拿着已有资源等别的）、**不可剥夺**（别人不能随意抢走）、**循环等待**（等待关系成环）。它们解释死锁可能出现的条件，并不是说满足后每次运行一定卡住。工程上常用**全局一致加锁顺序**打破循环等待；C++17 一次操作要拿多把锁时可用 `std::scoped_lock(a,b)`，其多锁构造采用避免死锁的加锁算法。

下面的两个账户是教学例子：`balance` 受各自 `mutex` 保护；转账要同时拿两把锁，且题设保证 `from`、`to` 不是同一对象。程序只执行安全路径，不故意运行会挂住的反例。

## 两笔转账怎样互相等住

假设账户 A 和 B 各有一把锁。线程 1 从 A 转到 B，先锁 A，再等 B；线程 2 同时从 B 转到 A，先锁 B，再等 A。两人都握着对方需要的锁，又都不肯先放手，就形成“线程 1 等线程 2，线程 2 等线程 1”的等待环。这不是单纯“程序跑得慢”，而是在没有外部干预时两条路径都无法推进。单次运行没卡住，只说明那次调度没碰上这个顺序，不能证明实现安全。

教材里的四个必要条件可这样记：锁一次只给一个线程使用（互斥）；已经拿住一把又去等另一把（占有并等待）；等待者不能直接抢走别人持有的锁（不可抢占）；等待关系围成环（循环等待）。它们是分析死锁的框架，不表示看到任意一条就一定死锁。工程上常用**统一锁顺序**打断等待环，例如无论转账方向如何都先锁编号较小的账户；C++17 也提供 `std::scoped_lock` 同时获取多把锁的接口。[C++17 lock 算法](https://timsong-cpp.github.io/cppwp/n4659/thread.lock.algorithm) 可核对多锁算法语义。

下方示例在 `transfer` 里先取得两个账户的锁，才修改双方余额。若只给单个余额加锁，另一个线程可能在转账中途观察到钱从 A 扣了却还没加到 B；所以锁既用来避免数据竞争，也把一笔转账的两个更新当成同一个受保护步骤。死锁、饥饿与数据竞争是不同问题：没有死锁也可能有线程长期拿不到执行机会，拿锁顺序正确也不自动使业务规则正确。

## 完整代码

```cpp
// C++17 安全示例：一次转账要同时占有两把锁，使用 scoped_lock 避免相反加锁顺序。
// 不执行可能死锁的反例；示例能正常结束不等于所有转账系统都没有死锁。
#include <cassert>  // assert：检查钱的总量守恒。
#include <iostream> // cout：打印最后余额。
#include <mutex>    // mutex、scoped_lock：保护共享余额并一起获取两把锁。
#include <thread>   // thread：模拟两个同时转账的执行流。

struct Account {
    int balance;      // 钱数用整数，避免本例讨论浮点舍入。
    std::mutex mutex{}; // 每个账户有自己的互斥锁；默认成员初始化也避免聚合初始化警告。
};

void transfer(Account& from, Account& to, int amount) {
    // 两个引用表示要操作的实际账户；本题保证 from 与 to 不同。
    std::scoped_lock both(from.mutex, to.mutex); // C++17 一起获取，离开函数自动解锁。
    from.balance -= amount; // 持锁时更新两个余额，不让别的线程看到中间状态。
    to.balance += amount;
}

int main() {
    Account a{100};
    Account b{100};
    std::thread first([&] { for (int i = 0; i < 100; ++i) transfer(a, b, 1); });
    std::thread second([&] { for (int i = 0; i < 100; ++i) transfer(b, a, 1); });
    first.join();  // 等两个线程都结束，才读最终余额。
    second.join();
    assert(a.balance + b.balance == 200);
    std::cout << "final balances: " << a.balance << ' ' << b.balance << '\n';
}
```

`std::scoped_lock both(...)` 是对象：创建时拿锁，作用域结束释放，这是旧课 [[学习/2026-10-20/02-RAII与异常清理|RAII]] 的应用。`join` 后主线程才读余额。若业务还涉及数据库或别的锁，只保护这两把锁不能保证整个系统无死锁。也不能把同一把非递归 mutex 重复传进去。

## 用两种实现检查等待环

先想错误写法：转出账户先上锁，再给转入账户上锁。A→B 的线程拿 A 等 B；B→A 的线程拿 B 等 A，就可能闭环。若只把一处加锁语句换个位置，没有全局规则，别的调用路径仍可能逆序。安全方案之一是给账户一个稳定编号，任何转账都先锁编号小者、再锁编号大者；另一个是示例中的 `std::scoped_lock` 一次处理两把锁。这里的“避免死锁”只针对这次多锁获取，不能覆盖锁内调用其它服务所形成的等待环。

代码里两条线程各转 100 次 1 元，方向相反。每次 `transfer` 同时保护 `from.balance` 和 `to.balance`，结束后两个线程 `join`，主线程才能稳定读取余额。`assert(a.balance+b.balance==200)` 检查总量守恒，但单靠总量仍抓不到“钱被错转给第三人”等业务错误；生产代码还要检查余额不足、金额是否合法、外部持久化失败等。锁解决的是并发访问与此处的原子观察边界，不自动验证业务规则。

面试碰到“死锁、活锁、饥饿”时也要分清：死锁是等待环使参与者无法前进；活锁可能不断改变状态却完成不了工作；饥饿是某个线程长期得不到所需资源。它们都表现为任务没完成，但排查证据和解决方法不同。

**面试口述**：死锁是线程互相持有资源又等待对方资源，形成无法推进的循环。识别四个必要条件；多锁操作统一顺序，或用 `std::scoped_lock` 一次获取。它只解决指定锁的一次获取，业务层其他等待仍要分析。
