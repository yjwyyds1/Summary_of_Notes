# 01 · 进程和线程到底差在哪里

← [[学习/学习导航/2026-10-24-学习导航|学习导航]] · [[八股测试/2026-10-24#OS-PROCESS-001 · 进程与线程有什么区别|自测题]] · [[学习/2026-10-24/示例代码/01_process_thread|代码阅读版]]

**进程**是正在运行的程序的一个实例，操作系统给它独立的虚拟地址空间等资源；**线程**是在进程内部执行指令的路径。地址空间是程序可使用的虚拟地址范围。同进程线程共享全局变量、堆与打开文件等进程资源，但各有自己的栈、寄存器状态。**栈**可先理解成函数调用的临时工作区；**堆**是动态分配对象通常所在的区域。

```mermaid
flowchart LR
  P["进程 A：地址空间/全局量/堆"] --> T1["线程 1：自己的栈"]
  P --> T2["线程 2：自己的栈"]
  Q["进程 B：另一地址空间"] -. "IPC 交换消息" .-> P
```

“共享地址空间”不等于访问天然安全：两个线程同时读写同一个普通变量，缺少同步可能形成数据竞争。旧课 [[学习/2026-10-20/04-shared_ptr与线程安全|线程与 mutex 入门]] 已讲这个前置；今天新学的是**进程边界**。两个进程的同名普通变量通常各有一份；要交换数据须用管道、共享内存等 IPC。Linux 的 `fork` 生成子进程后看似得到父进程内存的副本；常见实现用写时复制节约物理复制成本，但双方修改普通变量不会自动互通。

## 用一个程序想清“共享”和“隔离”

设想一个行情程序有两个线程：一个从网络读数据，另一个处理数据。它们属于同一个进程，看到的是同一进程的全局变量和动态分配对象；若都修改同一个队列，就必须约定锁或其它同步。每个线程有自己的执行位置、寄存器和调用栈，但“栈属于某线程”不表示它的地址天然禁止同进程其它线程访问：只要把仍有效的对象地址交出去，另一线程也可能访问它，生命周期和同步都要管好。

换成两个进程，默认各有一套虚拟地址空间。Linux `fork()` 在父进程返回子进程 ID，在子进程返回 0，因此一行代码之后父子走不同分支。它们都可能看到名为 `parent_value` 的变量和相同的**虚拟地址数值**，但修改普通内存不会自动传到对方。Linux 常用写时复制：初期可共享物理页，写入时再安排独立页。这是实现上的节约，不改变“父子逻辑上分别拥有自己的普通变量”的结论。[fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html) 给出具体平台语义。

读下方程序时抓住两个同步点：`worker.join()` 保证线程工作结束后主线程才检查共享变量；`waitpid()` 等子进程结束，并通过退出状态取得它报告的数字。退出码只适合很小的状态信息，不是传大量行情的 IPC。进程间若要传实际数据，下一篇会比较管道和共享内存。选择线程还是进程时先看隔离与共享需求，再考虑性能，不能背“线程一定比进程快多少倍”。

## 完整代码与运行过程

先看同进程线程把 `shared_in_process` 改为 2；主线程 `join` 后再读。Linux 分支随后 `fork`，子进程把自己的 `parent_value` 改为 9，父进程仍看到 1。Windows 分支只提示无法运行这个 Linux 系统调用。代码里 `[&shared_in_process]` 的 `&` 表示 lambda 借用外围变量；被借用变量必须活到线程结束。

```cpp
// C++17 教学示例：线程能修改同一进程的共享对象；Linux fork 后子进程修改的是自己的地址空间。
// Linux fork 分支不在 Windows 执行；代码不打印真实地址，也不把相同虚拟地址误说成同一物理内存。
#include <cassert>  // assert：核对预期结果。
#include <iostream> // cout：展示最终数值。
#include <thread>   // std::thread：创建并等待一个线程。
#ifdef __linux__
#include <sys/wait.h> // waitpid、WIFEXITED、WEXITSTATUS：回收子进程并读退出码。
#include <unistd.h>  // fork、_exit：创建进程与结束子进程。
#endif

int main() {
    int shared_in_process = 1; // main 与下面的线程属于同一个进程。
    std::thread worker([&shared_in_process] {
        // 引用捕获让线程访问 main 中同一个 int；join 前该对象一直有效。
        shared_in_process = 2;
    });
    worker.join(); // 等线程结束，建立同步；之后 main 才读这个值。
    assert(shared_in_process == 2);
    std::cout << "thread changed parent value: " << shared_in_process << '\n';

#ifdef __linux__
    int parent_value = 1; // fork 后父、子各有自己的虚拟地址空间。
    const pid_t child = fork();
    if (child == -1) { std::cerr << "fork failed\n"; return 1; }
    if (child == 0) {
        parent_value = 9; // 子进程改自己的副本；父进程中的变量仍是 1。
        _exit(parent_value); // 用退出码把 9 传回；避免子进程继续运行 main。
    }
    int status = 0;
    if (waitpid(child, &status, 0) != child) { std::cerr << "waitpid failed\n"; return 1; }
    assert(WIFEXITED(status) && WEXITSTATUS(status) == 9);
    assert(parent_value == 1);
    std::cout << "parent after child exit: " << parent_value << '\n';
#else
    std::cout << "fork comparison requires Linux\n";
#endif
}
```

**场景**：同一服务内部共享队列可用线程；需要隔离故障或权限、独立部署时常用多进程，再设计 IPC。进程也可能映射共享内存，故“进程绝不共享任何内存”是错的。创建与切换成本受平台和负载影响，不能背固定倍率。

## 把代码和真实服务对应起来

程序开始只有主线程。创建 `worker` 后，同一个进程中有两条执行路径：主线程往下走，工作线程执行 lambda。lambda 捕获的是 `shared_in_process` 的引用，所以写入发生在同一对象上；`join()` 等工作线程结束后，主线程才检查 2。若把 `join()` 删掉就立即读，不但可能读到旧值，还可能因无同步的并发读写产生数据竞争。这里的关键不是“线程一定先执行”，而是 `join` 建立了确定的先后关系。

再看 Linux 分支：`fork()` 调用前只有一个 `parent_value=1`。调用后有父子两个进程，各自继续执行；子进程把自己的值改成 9，并用 `_exit(9)` 报告状态。父进程的普通变量仍为 1，`waitpid` 只负责等待和取得退出状态，并没有把子进程的整块内存合并回父进程。若把退出码也误当作“共享变量”，就解释不了为什么退出码有范围和用途限制，更解释不了怎样传一段长消息。

真实服务常把连接处理拆到多个线程，因为共享内存让队列交接方便，但线程崩溃或写坏共享状态可能影响同一进程；把组件放在不同进程则能划出地址空间与权限边界，同时要承担通信和部署成本。选择前可问：数据是否高频共享？故障需要隔离到什么程度？是否跨机器？这三个问题比背诵“进程重、线程轻”更有用。

**面试口述**：进程是资源与地址空间隔离的运行实例，线程是进程里的执行流；同进程线程共享堆等资源、各有栈，通信方便但访问共享数据要同步。不同进程默认地址空间独立，交换数据靠 IPC。
