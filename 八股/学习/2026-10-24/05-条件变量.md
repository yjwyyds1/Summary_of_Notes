# 05 · 条件变量怎样让线程等状态改变

← [[学习/学习导航/2026-10-24-学习导航|学习导航]] · [[八股测试/2026-10-24#CON-CV-001 · condition_variable 为什么要配合锁和谓词|自测题]] · [[学习/2026-10-24/示例代码/05_condition_variable|代码阅读版]]

消费者还没拿到数据，不应反复 `if` 检查并占用 CPU。**条件变量**提供“条件不满足就等待，状态变化后再检查”的协调方式。它自己不存储“已有数据”这个事实；事实在受 mutex 保护的 `ready` 与 `value` 中。**谓词**就是返回 `true/false` 的条件检查函数。

```mermaid
flowchart LR
  C["消费者持锁检查 ready=false"] --> W["wait 释放锁并等待"]
  W --> P["生产者持锁写 value=42，ready=true"]
  P --> N["notify_one 通知"]
  N --> R["消费者重新持锁、检查 ready、读取"]
```

`cv.wait(lock, predicate)` 大致相当于在循环中 `while(!predicate()) cv.wait(lock)`：等待时释放锁，醒来后重新拿锁并检查。**虚假唤醒**指即使没有想要的事件也可能返回；多个消费者竞争时，别人也可能先取走数据。必须重查谓词，不能把 `notify_one()` 当作存好的一张“通知票”。`std::unique_lock` 能被 `wait` 解锁/重锁；普通 `lock_guard` 没有这个接口。

## 没有数据时为什么要“带着条件等待”

消费者真正关心的是 `ready == true`，而不是“有人通知过我”。先由同一把 mutex 保护 `ready` 和 `value`：生产者持锁写值并把 `ready` 设为真；消费者持锁检查条件。若条件仍是假，`wait` 会把**释放锁与开始等待**作为一项协调操作；醒来后先重新拿锁，再重查条件。这样生产者有机会取得锁并改变状态。若消费者抱着锁睡觉，生产者永远拿不到锁去写数据。[C++ condition_variable 条款](https://eel.is/c++draft/thread.condition.condvar) 明确了等待时解锁、醒来重新上锁的行为。

通知可以先于消费者进入 `wait`：如果那时 `ready` 已为真，谓词立即通过，消费者根本不必睡。通知也可能来了却不是你要的事件，甚至发生**虚假唤醒**；所以不能把“醒了”当作“数据一定可取”。`cv.wait(lock, predicate)` 把“醒后重新检查”写成接口的一部分。`std::unique_lock` 能在等待时释放并重新获取锁，普通 `lock_guard` 不提供这一操作。

读代码时分别指认三样东西：`ready/value` 是事实，mutex 防止并发访问事实时读写相撞，条件变量负责让线程在条件未满足时睡眠并被唤醒。关闭队列时还要把“已关闭”放进谓词，并唤醒所有可能等待的线程；只 `notify_all()` 却不改变受保护状态，醒来的线程仍会发现条件不满足而继续等待。

## 完整代码

```cpp
// C++17 条件变量：消费者在“还没有数据”时睡眠，生产者写数据后发通知。
// 使用谓词版 wait，避免虚假唤醒或通知先到造成逻辑错误。
#include <cassert>            // assert：检查消费者最终拿到的值。
#include <condition_variable> // condition_variable：等待与通知。
#include <iostream>           // cout：展示结果。
#include <mutex>              // mutex、unique_lock、lock_guard：保护共享状态。
#include <thread>             // thread：创建消费者线程。

int main() {
    std::mutex mutex;                 // ready 和 value 都受同一把锁保护。
    std::condition_variable changed; // 通知“共享状态可能变化了”。
    bool ready = false;              // 真正的条件：数据是否已经准备好。
    int value = 0;
    int consumed = 0; // 只由工作线程写；join 后主线程才读。

    std::thread consumer([&] {
        std::unique_lock<std::mutex> lock(mutex); // wait 需要可解锁/重锁的锁对象。
        changed.wait(lock, [&] { return ready; }); // 等待时释放锁，醒后重锁并重新查 ready。
        consumed = value; // 此时持锁，读到与 ready 一起发布的值。
    });

    {
        std::lock_guard<std::mutex> lock(mutex); // 作用域结束自动解锁。
        value = 42;
        ready = true; // 先改变条件，再通知；谓词决定是否继续等待。
    }
    changed.notify_one(); // 唤醒一个等待者；即使先于 wait，ready 仍能被检查。
    consumer.join();
    assert(consumed == 42);
    std::cout << "consumed: " << consumed << '\n';
}
```

**场景**：工作线程等任务、消费者等队列非空、主线程等阶段完成。状态应在同一 mutex 约束下更新和检查；先把状态发布正确，再通知。`notify_one` 唤醒一个等待者，`notify_all` 可用于关闭时让所有人退出。队列版见 [[学习/2026-10-24/07-练习-有界队列|今日练习]]。

## 手推两种执行顺序

第一种是消费者先跑：它拿锁看见 `ready=false`，进入带谓词的 `wait`，等待过程释放 mutex。生产者随后拿锁写 `value=42`、设置 `ready=true`，释放锁再 `notify_one`。消费者被唤醒后重新拿锁，谓词为真，才把 42 读入 `consumed`。最后主线程 `join` 后检查结果。

第二种是生产者先跑：它先把值和 `ready` 更新好，甚至通知也发完了；消费者之后才进入 `wait(lock, predicate)`。这时第一次检查就看见 `ready=true`，不会真正睡下去。通知并没有被“缓存”，使结果正确的是持久保存在共享状态里的 `ready`。这也解释为什么不能写成“先等通知，再读变量”。

再加一个虚假唤醒：消费者醒来却发现 `ready` 仍是假，谓词版 `wait` 会继续等待。若队列里有多个消费者，通知一个也不保证醒来的那个最终拿到数据，因为拿锁和竞争会改变状态。关闭协议因此通常写成 `ready || closed` 之类的谓词，让等待者有办法在没有数据时退出；只调用 `notify_all` 却不修改状态，线程很可能继续睡。

**面试口述**：条件变量等待共享状态变化。状态由 mutex 保护，等待者用 `unique_lock` 加谓词 `wait`；等待会释放锁，返回前重获锁并重查谓词。生产者更新状态再通知。条件变量不是状态本身，也不缓存通知。
