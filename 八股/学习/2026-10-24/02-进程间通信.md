# 02 · 两个进程怎样交换数据

← [[学习/学习导航/2026-10-24-学习导航|学习导航]] · [[八股测试/2026-10-24#OS-IPC-001 · 进程间通信有哪些方式|自测题]] · [[学习/2026-10-24/示例代码/02_pipe_ipc|代码阅读版]]

**IPC** 是 inter-process communication，即进程间通信。上一页的普通变量在父子进程中各有一份，不能靠 `x=1` 给另一个进程发消息。面试先问“要传什么、是否同机、是否双向、数据量与同步要求”，再比较机制。

| 机制 | 普通理解 | 用途与边界 |
| --- | --- | --- |
| 匿名管道 | 内核提供单向字节通道，有读端/写端 | 父子进程传数据；无消息边界，容量有限 |
| 共享内存 | 多进程映射同一段内存 | 同机大量数据；不自动解决互斥、通知或版本 |
| socket | 用端点交换数据，可本机/跨机 | 仍须协议；TCP 字节流定界见 [[学习/2026-10-23/04-TCP消息边界|旧课]] |

本例 `pipe(ends)` 得到 `ends[0]` 读端、`ends[1]` 写端。下面先建管道再 `fork`，父子都继承端点；子进程关掉不用的读端，父进程关掉不用的写端。**fd**（file descriptor）是 Linux 给打开资源的整数编号，`ends` 数组里存的就是两个 fd；`read` 返回读到的字节数，所有写端关闭且数据读尽时返回 0。示例只发固定短字符串；实际协议还要处理部分读写、`EINTR` 和错误。

## 让两个进程交换一条消息

**IPC** 是进程间通信。因为普通变量各归各的地址空间，子进程执行 `message = "ABC"` 并不会使父进程的同名变量改变。管道提供内核维护的一条字节通道：`pipe(ends)` 取得读端 `ends[0]` 与写端 `ends[1]`；`fork()` 后父子都继承这些描述符，约定子进程只写、父进程只读。写入 `ABC` 后，父进程从读端取回字节，这才是跨进程传输，不是“共享了同一个普通变量”。[pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html) 说明管道是字节流，读写次数与应用消息数不必一致。

两边应及时关闭不用的一端：子进程关闭读端，父进程关闭写端。若某处还留着打开的写端，读端即使暂时没有数据，也可能一直等不到真正的 EOF。读写还可能短于请求长度、被信号打断或失败；演示程序发送很短的一段数据，生产代码必须按返回值循环处理。匿名管道通常用于有继承关系的进程；不相关进程还可考虑命名管道、Unix domain socket 或命名共享内存。

共享内存走另一条路：两个进程把同一个共享对象映射进各自地址空间，可以直接读写同一片字节，但“看得到同一片”不等于“知道何时写完”。要另外定义记录格式、可见顺序、进程间同步、崩溃后的恢复和所有权。把普通 `std::mutex` 对象随便放进共享区域，并不能自动得到正确的跨进程锁语义。跨机器时还要用网络通信；同机共享映射不能直接变成跨机内存。对小量控制消息，先用语义清楚的通道；确有大量数据与测量证据，再考虑共享内存的额外复杂度。

## 完整代码

```cpp
// C++17 / Linux 示例：父子进程用匿名管道传递三个字节。
// Windows 上只显示平台提示；管道是字节流，不保证一次 write 对应一次 read。
#include <iostream> // cout/cerr：结果与错误信息。
#ifdef __linux__
#include <sys/wait.h> // waitpid：回收子进程，避免僵尸状态。
#include <unistd.h>  // pipe、fork、read、write、close、_exit。
#endif

int main() {
#ifdef __linux__
    int ends[2]; // ends[0] 是读端，ends[1] 是写端。
    if (pipe(ends) == -1) { std::cerr << "pipe failed\n"; return 1; }
    const pid_t child = fork();
    if (child == -1) { close(ends[0]); close(ends[1]); return 1; }
    if (child == 0) {
        close(ends[0]); // 子进程不读；关闭不用的一端。
        const char data[3] = {'A', 'B', 'C'};
        const ssize_t sent = write(ends[1], data, sizeof data);
        close(ends[1]); // 关闭最后写端，父进程读完后能看到 EOF。
        _exit(sent == 3 ? 0 : 1);
    }
    close(ends[1]); // 父进程不写，否则自己的写端会妨碍判断 EOF。
    char buffer[3]{};  // 足够存三个字节，无需 C 字符串终止符。
    std::size_t used = 0;
    while (used < sizeof buffer) {
        const ssize_t n = read(ends[0], buffer + used, sizeof buffer - used);
        if (n < 0) { close(ends[0]); waitpid(child, nullptr, 0); return 1; }
        if (n == 0) break; // 所有写端已关闭，且管道中没有剩余数据。
        used += static_cast<std::size_t>(n); // read 可能只交付部分字节。
    }
    close(ends[0]);
    int status = 0;
    if (waitpid(child, &status, 0) != child) return 1;
    if (!WIFEXITED(status) || WEXITSTATUS(status) != 0 || used != 3) return 1;
    std::cout << "parent received: ";
    std::cout.write(buffer, static_cast<std::streamsize>(used));
    std::cout << '\n';
#else
    std::cout << "pipe/fork example requires Linux\n";
#endif
}
```

**何时选**：简单父子进程单向传输先考虑管道；大量同机数据可评估共享内存，但同步协议复杂；跨机器可考虑 socket。“共享内存必定最快”缺少数据大小、缓存和同步前提。线程本就共享进程地址空间，线程队列通常不叫 IPC。

## 顺着父子进程各走一遍

代码先建管道再 `fork`，所以父子各有读、写两个描述符。子进程关掉自己不用的读端，写入 `ABC`，再关闭写端。父进程关掉自己不用的写端，用 `used` 记录已经读到多少字节：若第一次只读到 `A`，下一次的目标地址是 `buffer+1`，最多还读 2 字节。它循环直到凑够三个字节或看到 EOF。`cout.write(buffer, used)` 显式给出长度，因为 `buffer` 只有三个字节，没有用于 C 字符串的末尾零字节。

容易困惑的是“为什么关掉不用的写端”。EOF 的前提是所有写端都关闭且管道中数据已取完；父进程若保留自己的写端，即使子进程退出，内核仍看到一个打开的写端。一个等待 EOF 的读循环便可能一直等。关闭描述符也是协议的一部分，不只是节约资源。此例按已知长度读取，实际传可变长消息时还要约定长度前缀或结束标志，并对读到 0、短写、被信号打断分别处理。

比较三种方式时可想一份 1 MiB 数据：管道与 socket 以字节流传输，双方要处理读写进度；共享内存让双方访问同一映射，但要规定写者何时完成、读者何时能读，以及崩溃后如何判断数据是否有效。因而“少复制”只解决其中一部分成本，不能直接推出整个系统更快。

**面试口述**：管道是内核维护的单向字节流；共享内存让多个进程访问同一映射，减少某些数据复制，但互斥和通知必须另做。选择看机器边界、消息语义、吞吐与复杂度。
