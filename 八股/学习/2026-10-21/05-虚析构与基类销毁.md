# 05 · 虚析构与基类销毁

这一篇回答：拿着统一接口时，怎样把真实派生对象完整销毁？
上一题解决“业务调用哪一个实现”，本题解决“最终销毁谁”。
基线固定为 **C++17**，核验日期为 **2026-10-21**。
错误删除例子只用于阅读分析，不放进可执行源文件，也不运行来猜输出。

## 1. 先解释析构与两种类型

**析构函数**是对象结束生命时负责执行清理的特殊成员函数。
写法为 `~类名()`，没有返回类型、没有形参。
它的函数体结束后，成员和基类子对象还会按语言规则继续自动销毁。

**基类子对象**是完整派生对象内部的基类部分。
一个 `FileChannel` 对象里包含一个 `Channel` 基类子对象。
持有 `Channel*` 可以指向这一部分；完整对象仍是 `FileChannel`。

**静态类型**是从声明和表达式中确定的类型。
对于 `Channel* pointer`，经该指针看对象时，接口类型是 `Channel`。

**动态类型**描述这里实际存在的最派生对象类型。
如果它来自 `new FileChannel`，真实完整对象类型就是 `FileChannel`。
把指针转成基类指针不会把对象复制成基类值。

**虚析构函数**是在基类声明为 `virtual` 的析构函数。
它使经基类指针删除真实派生对象时，能够选择正确的派生析构入口。
后续的成员与基类销毁，由正常析构规则继续完成。

不要把“释放一块存储”和“完整执行对象销毁”合成一个模糊动作。
对象可能持有字符串、文件句柄或其他成员资源。
正确销毁不仅要收回外层内存，还要执行对应类型的清理过程。

## 2. 最重要的 C++17 结论

考虑普通单对象 `delete pointer;`：

- 指针指向由对应 `new` 创建的对象或其基类子对象。
- 删除时的静态对象类型和真实动态类型不同。
- 静态类型是动态类型的基类。
- 在这种情形下，基类必须有虚析构，否则行为未定义。

因此，`Base* p = new Derived;` 后执行 `delete p;`，
若 `Base` 的析构函数非虚，即使程序能编译，也不能认为它正确。

**不能把结论说成“标准保证只执行 Base 析构”。**
这是未定义行为，语言不保证固定输出、固定泄漏方式或固定崩溃方式。
一次运行“看起来正常”不能修复违反的规则。
依据：[N4659 §8.3.5 expr.delete/3](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/expr.delete#3)。

此处只讨论普通 C++17 单对象删除。
不要把较新标准的 destroying delete 规则借来修改今天的结论。
数组 `delete[]` 也不能照搬这种基类多态删除设计。

## 3. 完整程序：拥有者存基类类型，真实对象完整销毁

源码：[[学习/2026-10-21/示例代码/05_virtual_destructor.cpp|05_virtual_destructor.cpp]]  
代码阅读页：[[学习/2026-10-21/示例代码/05_virtual_destructor|完整代码与练习]]

```cpp
// C++17：虚析构保证 unique_ptr<Channel> 能完整销毁真实派生对象。
// 所有可执行路径都安全；非虚析构的错误设计仅在配套 Markdown 中静态分析。

#include <cassert>   // 提供 assert：核对析构前后的计数。
#include <iostream>  // 提供 std::cout：观察构造、业务与析构顺序。
#include <memory>    // 提供 std::unique_ptr 和 std::make_unique。
#include <string>    // 提供 std::string：保存通道名称。

// 一个小计数器：在拥有者销毁后仍能检查两个析构函数是否执行。
struct LifetimeCount {
    int derived = 0;  // 派生类析构函数体执行次数，起始为 0。
    int base = 0;     // 基类析构函数体执行次数，起始为 0。
};

// Channel 是抽象通信接口：调用者可使用，也可通过基类拥有并销毁它。
class Channel {
public:
    // 接收一个已存在计数器的引用；本类不拥有该计数器。
    explicit Channel(LifetimeCount& counts) : counts_(counts) {
        std::cout << "Channel ctor\n";
    }

    // public 允许外部删除；virtual 使删除遵循真实派生类型。
    // 析构函数不能写返回类型；它不是普通的 void 成员函数。
    virtual ~Channel() {
        ++counts_.base;  // ++ 把计数加一，记录基类析构函数体执行。
        std::cout << "Channel dtor\n";
    }

    // = 0 让 Channel 保持抽象；const 表示调用不修改普通成员。
    virtual int send() const = 0;

private:
    LifetimeCount& counts_;  // 非拥有引用；main 保证计数器活得更久。
};

// FileChannel 是一个具体通道；final 表示不再继续派生。
class FileChannel final : public Channel {
public:
    // 两个形参分别提供计数器和名称；名称以 const 引用避免形参复制。
    FileChannel(LifetimeCount& counts, const std::string& name)
        : Channel(counts), name_(name), counts_(counts) {
        // 先构造基类，再按声明顺序初始化 name_、counts_，最后进入此处。
        std::cout << "FileChannel ctor\n";
    }

    // 基类析构已经 virtual，因此派生析构可用 override 核对覆盖关系。
    ~FileChannel() override {
        ++counts_.derived;  // 只记录派生析构函数体，不手工调用基类析构。
        std::cout << "FileChannel dtor\n";
        // 函数体结束后自动销毁本类成员，再自动销毁 Channel 基类子对象。
    }

    // override 核对 send 的返回类型、参数和 const 都与基类要求兼容。
    int send() const override {
        std::cout << "send: " << name_ << '\n';
        return 7;  // 教学用固定返回值，不进行真实文件或网络操作。
    }

private:
    std::string name_;       // 拥有名称文本；析构会自动清理其内部资源。
    LifetimeCount& counts_;  // 借用同一个计数器，供派生析构记录。
};

int main() {  // 程序入口；以下花括号用来明确拥有者的销毁时刻。
    LifetimeCount counts;  // 在内层作用域之前创建，在其之后才销毁。

    {
        // make_unique<FileChannel> 创建真实 FileChannel。
        // 转为 unique_ptr<Channel> 后仍是同一对象，并未复制成 Channel。
        std::unique_ptr<Channel> channel =
            std::make_unique<FileChannel>(counts, "quotes");

        // -> 通过智能指针访问对象；虚调用进入 FileChannel::send。
        const int result = channel->send();
        assert(result == 7);
        assert(counts.derived == 0 && counts.base == 0);

        std::cout << "before owner leaves\n";
    }  // channel 析构：默认删除器经 Channel* 删除，虚析构选择完整链条。

    // 内层拥有者已经退出，外层计数器还活着，可以安全读取。
    assert(counts.derived == 1);
    assert(counts.base == 1);
    std::cout << "after owner leaves\n";
    return 0;
}
```

## 4. 顺着输出理解每一步

在不改变源码、不定义 `NDEBUG` 禁用断言的情况下，断言用于核对演示条件。
程序按语言规则预期输出如下；实际编译运行记录由当天统一验证补充。

```text
Channel ctor
FileChannel ctor
send: quotes
before owner leaves
FileChannel dtor
Channel dtor
after owner leaves
```

第一行先出现基类构造，再出现派生构造。
因为派生部分建立之前，内部基类部分必须先存在。
`send: quotes` 说明基类智能指针的虚调用进入真实派生实现。

`before owner leaves` 时，拥有者仍在内层作用域里。
此时两个析构计数都为零。
遇到右花括号，`channel` 这个局部智能指针结束生命，触发其删除行为。

真实对象先进入 `FileChannel::~FileChannel`。
函数体执行完后，`name_` 等本类成员按规则销毁。
引用成员本身结束存在，不会因此销毁外层的 `counts` 对象。
随后进入 `Channel::~Channel`，清理基类部分。

`after owner leaves` 出现在完整析构之后。
计数器仍属于外层作用域，因此最后两条断言读取它是安全的。
如果把计数器先销毁而仍让析构访问其引用，就会是另一个生命周期错误。

析构顺序依据：[N4659 class.dtor/9–10](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/class.dtor)。
这里打印的是析构函数体，并没有打印所有成员对象的内部析构动作。

## 5. 图解：选择派生入口，再沿正常析构链向下完成

**可编辑关系图（Mermaid）**

```mermaid
flowchart LR
  A["unique_ptr<Channel> 拥有 FileChannel"] --> B["经 Channel* delete"]
  B --> C["virtual ~Channel 选中完整派生销毁入口"]
  C --> D["FileChannel 析构体"]
  D --> E["派生成员 name_ 销毁"]
  E --> F["Channel 析构体"]
  F --> G["释放对象存储"]
```

读图时注意两段机制：

1. 基类虚析构解决“从哪一个真实类型的析构函数进入”。
2. 正常析构规则解决“成员与基类部分按什么次序继续销毁”。

派生析构里不需要再手工写 `Channel::~Channel();`。
手工调用基类析构不会替你建立正确的拥有关系，反而可能重复结束生命。
完整对象的销毁不是“所有析构函数各自随意被调用一次”。
它有严格的入口、成员顺序和基类顺序。

基类析构是虚的，派生析构会继续是虚的。
派生类写 `~FileChannel() override` 是很有用的编译期检查。
它不要求派生析构的函数名与基类字面一致；析构覆盖有专门语言规则。
依据：[N4659 class.dtor/10](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/class.dtor#10)。

## 6. 为什么 unique_ptr 也需要正确的基类析构契约

昨天已经学过独占所有权；今天只补它与多态销毁相接的地方。
`unique_ptr<T>` 默认使用 `default_delete<T>`。
拥有者销毁时调用删除器；对普通单对象，默认删除器最终使用 `delete`。

当类型是 `unique_ptr<Base>` 时，默认删除器的对象类型也是 `Base`。
从 `unique_ptr<Derived>` 转进来，不等于默认删除器永远记住 `Derived`。
如果最终经 `Base*` 删除真实派生对象，仍要满足本题的虚析构规则。

```cpp
// 仅作错误设计分析，不加入可执行示例；这里省略类定义。
// 前提：Base 的析构可访问但非虚，Derived 公开继承 Base。
std::unique_ptr<Base> owner = std::make_unique<Derived>();
// owner 销毁时，默认删除器经 Base* 删除真实 Derived：行为未定义。
```

智能指针能负责“何时按其删除策略执行清理”。
它不能替错误的类型契约创造语言保证。
所以“已经用了 RAII，就可以不管基类析构”是错误结论。

本题使用 `unique_ptr<Channel>` 并将析构声明为 public virtual，
正是把所有权策略与类层级的销毁契约接起来。
标准库依据：[N4659 unique.ptr，含 default_delete 与析构条款](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/unique.ptr)。

## 7. public virtual 与 protected non-virtual 怎么选

Core Guidelines C.35 给出一个常用工程建议：
基类析构要么 public virtual，要么 protected non-virtual。
这是指导类接口设计的建议，不是“所有继承语法必须如此”的语言定律。
来源：[官方 C++ Core Guidelines C.35](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c35-a-base-class-destructor-should-be-either-public-and-virtual-or-protected-and-non-virtual)。

### 7.1 允许外界经基类销毁：public virtual

```cpp
class OwningInterface {
public:
    virtual ~OwningInterface() = default;  // 外部可删，且支持派生对象。
    virtual void run() = 0;                // 普通业务能力另行声明。
};
```

适合 `unique_ptr<OwningInterface>` 这样的基类拥有者。
调用者使用统一类型，同时有权负责完整对象的最终销毁。

### 7.2 禁止外界经基类销毁：protected non-virtual

```cpp
class BorrowedInterface {
public:
    virtual void run() = 0;  // 外界可以借用接口发起业务调用。

protected:
    ~BorrowedInterface() = default;  // 外部无权经该基类析构。
};
```

`protected` 允许派生类在自己的析构过程中销毁基类部分。
普通外部代码不能 `delete BorrowedInterface*`，访问检查会阻止它。
默认 `unique_ptr<BorrowedInterface>` 的删除器也不能任意绕过这个限制。

具体派生类仍可拥有 public 析构，并由具体类型拥有者管理。
这种设计表达“可以借用接口，但这里不提供经接口销毁的能力”。
类内部成员和友元仍需自行遵守删除规则；protected 不是运行时安全检查。

| 接口希望允许的动作 | 常见析构设计 |
|---|---|
| 外部统一拥有并经基类删除 | public virtual |
| 外部只借用，销毁由具体类型负责 | protected non-virtual |
| 两者都没有想清楚 | 先把所有权契约说清楚 |

## 8. shared_ptr 的重要例外与限制

不要把“unique_ptr 默认删除器”的推理机械套到所有 shared_ptr 创建方式。
shared_ptr 的共享拥有信息保留了创建所有权时确定的销毁方式。
因此，它的**指向类型**不一定等于最终销毁动作所依据的类型。

下面是安全情形的语法片段：

```cpp
struct PlainBase {
    ~PlainBase() = default;  // 此处故意非虚，仅用来解释这个特定例外。
};
struct PlainDerived : PlainBase {
    // 真正创建的是 PlainDerived，销毁时也使用对应完整类型。
};
std::shared_ptr<PlainBase> good = std::make_shared<PlainDerived>();
```

`make_shared<PlainDerived>` 建立的是针对真实派生对象的共享拥有关系。
之后转换成 `shared_ptr<PlainBase>`，并未重建为“经 Base* 普通 delete”。
所以这个特定构造路径的正确销毁不依赖 PlainBase 的虚析构。
`shared_ptr<Base>{new Derived}` 直接接收 Derived* 的构造路径也能保留对应类型。

但不能推出“shared_ptr<Base> 对非虚基类永远安全”。
若先把对象地址擦成 `Base*`，再用该指针建立默认共享拥有关系，
创建时看到的删除类型就是 Base，错误的普通删除契约并未得到修复。

```cpp
// 只分析，不执行；前提同上，Base 析构非虚且真实对象为 Derived。
Base* erased = new Derived;
std::shared_ptr<Base> bad{erased};
// 该创建/销毁路径要求 delete erased 正确；此前提不满足，不能使用。
```

自定义删除器也必须真的执行正确销毁，而不是名字叫 deleter 就安全。
不要因这个例外弱化接口规范：一般可被基类拥有的多态接口仍宜 public virtual。
依据：[N4659 shared_ptr 构造](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/util.smartptr.shared.const)、
[make_shared](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/util.smartptr.shared.create)、
[shared_ptr 析构](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/util.smartptr.shared.dest)。

## 9. 常见追问与边界

**没有新增成员的 Derived，也能经非虚 Base* 删除吗？**  
不能用“暂时没有资源”绕过 C++17 的删除规则。
这里的未定义行为取决于类型与虚析构条件，不取决于你是否看见泄漏。

**栈上创建一个具体 Derived，Base 析构非虚就一定错吗？**  
不是。具体对象正常离开作用域时，编译器知道完整类型。
本题危险条件是经不合适的基类指针删除真实派生对象。
不过基类接口设计仍要阻止调用方容易走错的路径。

**基类有普通虚函数，析构就自动 virtual 吗？**  
不会。基类析构必须自己声明 virtual，或从有虚析构的更上层基类继承这一性质。
抽象类同样不会自动替你补齐这个契约。

**虚析构能修复悬垂指针或重复 delete 吗？**  
不能。指针本身必须仍指向合法、尚未销毁且可由这条路径删除的对象。
虚析构只解决这一个类型层级下的销毁入口问题。

## 10. 练习：给拥有关系选契约

先回答，再展开答案：

1. `unique_ptr<Channel>` 为什么不能只依赖“智能”二字保证正确？
2. 派生析构里是否应该手工调用基类析构？
3. 如果接口只允许借用，怎么在编译期阻止外部经基类删除？
4. “shared_ptr<Base> 必须虚析构”这句话要怎样说才准确？

> [!tip]- 展开练习答案
> 1. 默认删除器仍要遵守普通 delete 的语言规则；基类虚析构契约不能缺席。
> 2. 不应该。函数体结束后成员和基类自动销毁，手工重复调用可能破坏生命周期。
> 3. 常见设计是 protected non-virtual 析构，并由合法具体拥有者控制寿命。
> 4. 先查创建共享拥有关系时保存的销毁方式。
>    `make_shared<Derived>` 再转成基类 shared_ptr 的特定路径能正确销毁 Derived；
>    先擦成非虚 Base* 再默认接管就没有这个保证。
>
> 严格语言结论核对：[N4659 expr.delete/3](https://www.ece.uvic.ca/~frodo/cppdraft/n4659/html/expr.delete#3)。
> 工程选择核对：[Core Guidelines C.35](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#c35-a-base-class-destructor-should-be-either-public-and-virtual-or-protected-and-non-virtual)。

## 11. 30–90 秒口述总结

在 C++17 中，经普通基类指针 delete 真实派生对象，基类要有虚析构。
否则是未定义行为，不能保证“只调用基类析构”。
正确虚析构先选中真实派生入口，再自动按派生、成员、基类的规则完成清理。
unique_ptr<Base> 的默认删除器同样需要这个契约。
可被统一拥有的接口常用 public virtual 析构；只供借用可考虑 protected non-virtual。
shared_ptr 要追溯创建时的销毁策略，make_shared<Derived> 再转基类是重要例外。
