## 1. 先把几个词翻译成普通话

假设程序正在处理任务，运维希望它停止。运维工具不可能直接跳进程序的 `main` 调用某个 C++ 方法，操作系统可以替它传递一类简短通知，这就是**信号**。

| 名词 | 普通解释 | 准确边界 |
| --- | --- | --- |
| 信号 signal | 内核交付给进程或线程的事件通知 | 可以来自其他进程、内核事件或程序自己；每种信号有编号和默认动作 |
| 处理方式 disposition | 收到这类通知以后怎么做 | 常见选择是默认动作、忽略，或调用程序安装的处理函数 |
| 信号处理器 handler | 收到通知时临时执行的小函数 | 会打断正常执行，返回后通常回到被打断的位置；它不自动创建一个工作线程 |
| 待处理 pending | 通知已经产生，还没交付处理 | 例如信号暂时被阻塞 |
| 信号掩码 mask | 当前线程暂时不接收哪些信号 | 阻塞通常意味着延后交付，和忽略不是一回事 |
| 异步信号安全 | 在可能打断普通代码的处理器里仍可安全使用 | 和“多线程安全”不是同一个条件 |

Linux 中，某种信号的处理方式由进程内各线程共享，信号掩码则属于各个线程；发给进程的信号与指定给某线程的信号也有区别。本篇只编写**单线程**程序，先避开多线程信号路由。参见 [signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)。

## 2. `kill` 的名字容易让人误会

命令行里的 `kill` 和 C/POSIX 接口 `kill(pid, sig)` 都在发送信号；`kill` 这个名字不表示每次都强制结束目标。命令不指定信号时通常发送 `SIGTERM`。C 接口则需要明确给出 `sig`，没有“省略第二个参数”的写法。[kill(1)](https://man7.org/linux/man-pages/man1/kill.1.html)、[kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html)

| 写法或信号 | 意图与默认行为 | 目标程序能做什么 |
| --- | --- | --- |
| `kill PID` / `kill -TERM PID` | 发送 `SIGTERM`，默认动作是终止 | 可以安装处理器，把请求转成有序退出；也可以阻塞或忽略，因此不保证马上退出 |
| `kill -9 PID` / `kill -KILL PID` | 发送 `SIGKILL`，请求内核强制终止 | 不能捕获、阻塞或忽略，没有执行用户态收尾代码的机会 |
| `SIGUSR1` | 给应用自己定义用途的信号，默认动作也是终止 | 本示例先安装处理器，再把它解释为“停止工作” |
| `SIGSTOP` | 强制暂停执行，默认不是终止 | 和 `SIGKILL` 一样不能捕获、阻塞或忽略；不要把“停止”和“杀死”混成一个动作 |

上表描述 Linux 信号行为，程序中优先使用信号名字，避免依赖不同平台的编号。不可捕获等限制见 [signal(7) 的标准信号表](https://man7.org/linux/man-pages/man7/signal.7.html)。

对 `kill(pid, sig)`，内核需要找到目标并检查发送权限，再按信号语义产生/交付通知。目标未必立刻运行处理器：它可能暂时屏蔽这个信号。返回成功也不能当成“业务清理已经做完”。本篇只讨论正 PID 指定单个进程，进程组发送规则见 [kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html)。

## 3. 为什么不直接在处理器里清理

假设主流程已经进入输出库，正在更新缓冲区，信号恰好在更新一半时到达。处理器再调用同一个输出库，可能重入一个尚未保持一致的数据结构。如果主流程持有某把锁，处理器再次获取同一把锁，还可能等待永远无法完成的事情：被打断的主流程只有等处理器返回，才能继续释放锁。[signal-safety(7)](https://man7.org/linux/man-pages/man7/signal-safety.7.html)

因此不能因为“这函数线程安全”就把它放入处理器。`std::cout`、`printf`、普通动态分配、一般互斥锁操作都不能作为本篇处理器的安全写法。POSIX 确实列出了可在处理器中调用的函数，但随意拼接复杂业务仍容易出错。

这里采用容易检查的方案：**处理器只把一个标记置为 1，主流程在合适位置检查它。**

```mermaid
flowchart LR
    A[正常处理工作] --> B[收到 SIGUSR1]
    B --> C[处理器只把标记设为 1]
    C --> D[返回普通执行流程]
    D --> E[检查标记并停止接新任务]
    E --> F[普通流程收尾和返回]
```

这个图没有承诺“信号一到，全部任务立刻完成”。停止接新任务、当前任务做完还是取消、最长允许等多久，都属于应用自己的关闭协议。

## 4. 完整可运行示例

用途是观察安全控制流。示例给**自己**发送 `SIGUSR1`，不依赖另一个终端，不操作其他进程。它不创建线程或子进程，正常运行立即结束。它演示的是单线程接收通知，不是完整服务停机框架。

入口：[[学习/2026-10-31/示例代码/03_signal|同名 Markdown 阅读版]] · [[学习/2026-10-31/示例代码/03_signal.cpp|可编译源码]]。

```cpp
// 目的：观察“信号处理器只记下请求，普通执行流程再处理请求”。
// 平台：Linux + C++17；使用 POSIX sigaction，不能直接当成纯标准 C++ 跨平台代码。
// 先修：函数、全局变量、if、for，以及 &obj 表示取得对象地址。
// 步骤：安装处理器 -> 确保 SIGUSR1 未被阻塞 -> 自己发信号 -> 主流程退出循环。
// 观察：全部输出都来自 main；处理器没有输出、分配内存或加锁。
// 程序不向其他进程发信号，不创建线程或子进程，不需要外部输入。

#include <csignal>   // std::sig_atomic_t、std::raise：信号标记类型与给自己发信号。
#include <cstdio>    // std::perror：仅在普通执行流程中打印系统调用错误。
#include <iostream>  // std::cout/std::cerr：普通流程的教学输出。
#include <signal.h>  // POSIX 的 sigaction、sigset_t、sigprocmask 等接口。

// 0 表示尚未请求停止，1 表示请求过停止。
// volatile sig_atomic_t 适合本例“同一线程的处理器与正常流程”之间的简单标记。
// 它不是 std::atomic，也不能据此推导 volatile 能解决多个线程的数据竞争。
volatile std::sig_atomic_t stop_requested = 0;

// extern "C" 指定 C 语言链接，匹配信号处理回调的接口形式。
// 参数 int 是收到的信号编号；本例只注册一种信号，不使用它，所以省略参数名。
// void 表示没有返回值；这里不调用库函数，只把停止标记置为 1。
extern "C" void on_signal(int) {
    stop_requested = 1;
}

int main() {
    // {} 先把结构体各成员初始化；struct 是为了明确这是类型而不是同名函数。
    struct sigaction action{};
    // 这里只保存函数入口地址，没有立即调用 on_signal。
    action.sa_handler = on_signal;
    action.sa_flags = 0;  // 使用最基本的处理方式，不启用额外行为标志。

    // sa_mask 是处理器执行期间额外阻塞的信号集合；用 API 初始化为空集合。
    if (::sigemptyset(&action.sa_mask) == -1) {
        std::perror("sigemptyset(action)");
        return 1;
    }
    // &action 让内核读取这份配置；nullptr 表示本例不保存原来的处理方式。
    if (::sigaction(SIGUSR1, &action, nullptr) == -1) {
        std::perror("sigaction");
        return 1;
    }

    // 信号屏蔽状态可从启动者继承。显式解除本例信号的阻塞，避免它一直待处理。
    // 必须先安装处理器，再解除阻塞；SIGUSR1 的默认动作是终止进程。
    sigset_t unblocked{};
    if (::sigemptyset(&unblocked) == -1) {
        std::perror("sigemptyset(unblocked)");
        return 1;
    }
    if (::sigaddset(&unblocked, SIGUSR1) == -1) {
        std::perror("sigaddset");
        return 1;
    }
    // 本例只有一个线程，所以使用 sigprocmask；多线程程序应另行设计信号接收。
    if (::sigprocmask(SIG_UNBLOCK, &unblocked, nullptr) == -1) {
        std::perror("sigprocmask");
        return 1;
    }

    // 最多执行五个模拟工作单元；第二个单元后给当前线程发送 SIGUSR1。
    for (int unit = 1; unit <= 5; ++unit) {
        std::cout << "完成工作单元 " << unit << '\n';
        if (unit == 2) {
            // 信号未被阻塞且已安装处理器；raise 在处理器返回后才返回。
            // raise 返回 0 表示成功，非 0 表示失败；不假定失败一定设置 errno。
            if (std::raise(SIGUSR1) != 0) {
                std::cerr << "raise 失败\n";
                return 1;
            }
        }
        if (stop_requested != 0) {
            // 此时已经回到 main，可以正常使用输出、RAII 与业务清理代码。
            std::cout << "主流程收到停止请求，不再开始下一个工作单元\n";
            break;  // 只退出 for，继续执行 main 后面的清理位置。
        }
    }

    std::cout << "主流程执行收尾并正常返回\n";
    return 0;  // 正常离开 main 的作用域；本例没有需要回收的线程或子进程。
}
```

在 Linux 或 WSL 的代码目录运行：

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic 03_signal.cpp -o 03_signal
./03_signal
```

### 输出怎么看

在系统调用成功、没有额外外部信号干扰的本例中，输出顺序为：

```text
完成工作单元 1
完成工作单元 2
主流程收到停止请求，不再开始下一个工作单元
主流程执行收尾并正常返回
```

没有工作单元 3，是因为第二次工作后 `raise` 触发处理器，把标记置为 1。处理器自己没有打印任何一行。

### 按执行顺序读代码

1. **`stop_requested` 活得足够久。** 它是全局对象，在 `main` 和处理器中都能访问。本例使用 `volatile std::sig_atomic_t` 保存简单的 0/1 标记，不写 `++`，也不操作容器或字符串。
2. **`action` 是配置对象。** `action.sa_handler = on_signal` 保存函数入口，不是执行函数。`&action` 是取它的地址，`sigaction` 根据这份配置安装处理方式；`nullptr` 表示不需要保存旧配置。
3. **`sa_mask` 控制处理器期间额外阻塞哪些信号。** 空集合不表示关闭所有保护：默认情况下，当前正在处理的同一种信号也会在处理期间被阻塞，本例没有开启改变该行为的标志。[sigaction(2)](https://man7.org/linux/man-pages/man2/sigaction.2.html)
4. **先安装，再解除 `SIGUSR1` 的阻塞。** 程序可能继承启动者的掩码，显式 `SIG_UNBLOCK` 让实验不依赖该状态。这段只适合这里的单线程前提；多线程程序通常使用 `pthread_sigmask` 规划接收线程。[sigprocmask(2)](https://man7.org/linux/man-pages/man2/sigprocmask.2.html)
5. **`raise` 让实验可重复。** 本例信号未阻塞，处理器会在 `raise` 返回前完成，因此随后检查能看到标记。这个顺序来自 `raise` 的接口语义，不能套到“另一个进程发来了信号，什么时候处理都一样”。[raise(3)](https://man7.org/linux/man-pages/man3/raise.3.html)
6. **`break` 只退出循环。** 之后仍能执行 `main` 的普通收尾，再 `return`。若作用域内有管理文件或内存的 RAII 对象，正常离开作用域才有机会按语言规则析构。

## 5. `volatile` 在这里为什么可以，在多线程里又为什么不够

`sig_atomic_t` 是适合与信号处理交互的整数类型；`volatile` 使这类访问按语言要求作为可观察访问处理。C++17 对**同一线程**内的普通执行和信号处理器访问 `volatile std::sig_atomic_t` 有专门规则。本例只有一个线程，并且只写简单标志，满足这里需要的有限用途。[N4659，§4.7.1 [intro.races] 第 21 段，§21.10.4 [support.signal]](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2017/n4659.pdf)

这不意味着“`volatile` 让任何变量变成线程安全”。若线程 A 普通写一个 `volatile bool`，线程 B 无同步地读它，`volatile` 没有建立线程间的同步关系。多个工作线程的停止协议应使用适当的原子/锁等机制；不能直接把本例全局变量复制进线程池。旧的线程安全先修见 [[学习/2026-10-20/04-shared_ptr与线程安全|数据竞争与同步]]。

同样，处理器的安全性并不来自“只做了一行”。一行 `std::cout << ...` 仍然可能调用复杂、不适合此处的库代码。

## 6. 在什么场景使用，退出顺序怎么选

C++ 后台服务收到停止请求后，可以在普通执行流中依次停止接收新工作、唤醒等待者、按策略处理已接收工作、等待工作线程结束、关闭资源。对行情处理服务，“停止接新数据”和“内存队列里的数据如何处理”要明确约定，不能仅凭进程退出就宣称处理完整。

本示例没有线程池，也没有队列，所以只演示“看到请求后不再启动下一个工作单元”。真实事件循环如果可能长时间阻塞，仅有标记还不够：还需要可靠的唤醒方案。可以后续学习同步等待信号或将通知接入事件循环；这些属于本库扩展，本篇不实现完整框架。

**RAII 的边界也要说清。** `SIGTERM` 的默认动作本身不会替 C++ 程序完成正常栈展开。只有程序捕获请求并走到正常清理路径，才谈得上让相应 RAII 对象析构。`SIGKILL` 不给这个机会，不能指望析构、用户态缓冲刷新或业务记录自动完成。操作系统最终回收进程资源，不等于应用完成了业务收尾。

## 7. 常见误解与追问

| 说法 | 应怎样修正 |
| --- | --- |
| “`kill` 总是强杀。” | 它发送指定信号；命令默认 `SIGTERM`，具体动作取决于信号和处理方式 |
| “`SIGTERM` 一定会优雅退出。” | 它只是允许应用设计这种路径；默认行为、忽略、阻塞和处理器写法都会影响结果 |
| “先 `kill` 成功，就可以认定目标清理完成。” | 发送成功与完成业务收尾是两个阶段，需要另外确认退出或关闭协议完成 |
| “处理器里加锁就安全了。” | 它可能打断持锁代码并自锁，且一般锁操作不满足异步信号安全要求 |
| “发送 100 次普通信号，就能当作精确的 100 条任务。” | 普通信号在待处理期间可合并，不能把它当精确消息计数器 |
| “`kill -9` 让用户态执行最后一段清理。” | `SIGKILL` 无法捕获，不存在这种用户处理器 |

普通信号的合并规则见 [signal(7) 的 Queueing and delivery semantics](https://man7.org/linux/man-pages/man7/signal.7.html)。本例的 0/1 停止请求不需要计数，重复收到请求仍是同一个“需要停止”的状态。

**变式：把 `SIGUSR1` 换成 `SIGTERM` 就是生产版吗？** 不是。除了同步修改注册与发送信号，还要设计线程接收规则、阻塞等待的唤醒、任务收尾策略、超时和失败处理。本例刻意不声称解决这些问题。

## 8. 面试口述

`kill` 的核心是发送信号，命令默认发送 SIGTERM，`kill -9` 发送 SIGKILL。SIGTERM 默认终止，但程序可以捕获它，把停止请求交给正常执行流程，再停止接任务和清理资源；SIGKILL 不能捕获、阻塞或忽略，不能依赖用户态析构和业务收尾。信号处理器会打断正常代码，所以要遵守异步信号安全，不能随意输出、分配内存或加锁。单线程示例可以让处理器只设置 volatile sig_atomic_t 标记，主流程看到后退出；这不是跨线程同步方案。发送成功也不等于目标已经完成清理。
