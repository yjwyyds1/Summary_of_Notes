# 用户态、内核态与系统调用

← [[学习/学习导航/2026-10-31-学习导航]] · [[八股测试/2026-10-31#OS-SYSCALL-001 · 用户态、内核态与系统调用|回到自测]]

本节新增目标：解释应用程序怎样在受限制的环境里请求操作系统服务，以及为什么“进入内核”不等于“换一个进程运行”。[[学习/2026-10-24/01-进程与线程|进程与线程]]、[[学习/2026-10-24/03-虚拟内存|地址空间与页表]]只作先修，不重新计为新题。

## 先想一个实际问题

行情程序已经在自己的数组中拿到了价格，计算两个价格的差只需执行普通指令。但要把日志交给终端、从网络读取数据，或者创建子进程，就涉及操作系统管理的资源。假如任何应用都能随意控制设备、改页表、读写别的程序的内存，一个程序的错误就可能破坏整个系统。

操作系统因此提供受控入口：应用说明“我要做什么、操作哪个资源、数据在哪里”，内核检查请求，按权限和资源状态完成操作，再返回结果。系统调用就是这样的一种请求方式。

## 名词先讲清楚

| 名词 | 普通解释 | 准确边界 |
| --- | --- | --- |
| 用户态 | CPU 正在以受限制的权限执行应用代码 | 不是“普通用户账号”；root 启动的应用也通常在用户态运行 |
| 内核态 | CPU 正在执行拥有系统特权的内核代码 | 不是另一台 CPU，也不必是另一个进程 |
| 用户空间 / 内核空间 | 地址空间里面向应用和面向内核的区域及访问边界 | “空间”谈地址与可访问性，“态”谈执行权限，不是同一个维度 |
| 系统调用 | 应用向内核请求服务的受控接口 | Linux 接口及其 ABI，不属于 ISO C++17 本身 |
| libc 包装函数 | 供 C/C++ 程序调用的一层库接口 | 可能做参数整理、错误转换；一个库函数不一定对应一次系统调用 |
| ABI | 编译出的机器代码彼此约定如何传参和返回 | 系统调用号、寄存器分配及进入指令会因体系结构而不同 |
| fd | 本进程用来指向一个已打开资源的整数编号 | 本例只需知道 1 通常是标准输出，-1 是非法编号 |
| `errno` | 失败时提供原因的错误编号 | 先看返回值确认失败，再读它；成功调用也可能改变旧值 |

`errno` 在 Linux libc 中是线程局部的，不是“全进程所有线程共用一份错误变量”；不要自己声明它。数字可能随平台变化，程序用 `EBADF`、`EINTR` 这样的符号名比较。[errno(3)](https://man7.org/linux/man-pages/man3/errno.3.html)

## 从普通调用走到内核，再走回来

一次普通的 `add(a, b)` 只需要调用约定；如果被编译器内联，连独立函数调用指令都不一定留下。系统调用还要通过体系结构规定的入口进入内核。以普通的读取请求为例：

1. 应用把 fd、缓冲区地址和长度交给库接口。
2. 包装层按系统调用 ABI 准备调用号和参数，执行进入内核的指令。以 x86-64 为例常见的是 `syscall` 指令；不是所有 CPU 都用同一条指令。
3. 内核入口保存必要状态、建立内核执行环境，再根据调用号分派服务。服务实现校验资源、用户地址和权限，并执行操作。
4. 若资源立即可用，可能直接完成；若必须等待，当前线程可能阻塞，调度器才可能安排其它线程运行。
5. 返回前处理必要的退出工作，恢复用户执行环境，库接口把结果交回程序。常见失败表示为 -1，并设置 `errno`。

这里说的“保存必要状态”不是把整个进程内存复制一遍。内核文档分别描述了系统调用、异常和中断的进入／退出路径；具体保存细节与架构相关。[Linux 内核入口文档](https://docs.kernel.org/core-api/entry.html)、[syscall(2)](https://man7.org/linux/man-pages/man2/syscall.2.html)

`syscall()` 是 libc 提供的通用函数，括号里的 `SYS_getpid` 才指定请求哪项内核服务。它与 x86-64 的 `syscall` 机器指令同名，但一个是源码 API，一个是处理器指令。日常开发优先使用 `read()`、`write()` 等标准包装接口；本例用通用函数只是为了把“调用号”展示出来。

```mermaid
flowchart LR
    U["用户态：准备参数"] --> L["libc：按 ABI 请求系统调用"]
    L --> K["内核入口：保存状态与检查请求"]
    K --> S["执行对应服务"]
    S --> R["返回结果并恢复用户执行环境"]
    R --> U2["同一线程继续用户代码"]
    S -. "需要等待时" .-> W["阻塞，可能调度其它线程"]
    W --> S
```

图的实线是一条可以不切换到其它线程的执行路径。虚线表示“可能发生调度”，不是每个系统调用都必经的一步。

## 进入内核的三类常见原因

| 原因 | 谁触发 | 例子 |
| --- | --- | --- |
| 系统调用 | 当前程序主动请求 | `read`、`write`、`fork` |
| 异常 | 执行当前指令时处理器发现条件 | 访问合法但暂未建立实际映射的页，触发缺页处理 |
| 硬件中断 | 设备或计时器通知 CPU | 网卡完成、时钟事件 |

只有事件发生时 CPU 原本在用户态，才能说这次事件引起了“用户态到内核态”。中断也可能发生在内核已经运行的时候。这里的“异常”是 CPU/操作系统层面的术语，不等于 C++ 的 `throw/catch`。[Linux 中断与异常入口](https://docs.kernel.org/core-api/entry.html#interrupts-and-regular-exceptions)

## 完整示例：实际请求内核并处理错误

阅读版：[[学习/2026-10-31/示例代码/01_syscall|01_syscall.md]]；源码：[01_syscall.cpp](示例代码/01_syscall.cpp)。以下源码与这两份文件同步。

```cpp
// Linux + C++17 教学示例：把普通计算、进入内核和系统调用失败分开观察。
// 前置：认识函数、指针、数组长度；只在 Linux 编译，无 Windows 替代分支。
// 步骤：普通加法 -> SYS_getpid -> SYS_write 输出 -> 非法 fd 返回 EBADF。
// 观察：syscall() 仍是 libc 函数，但它会通过体系结构规定的入口请求内核。
// 本例没有创建子进程、文件或线程；正常终端下立即结束，不用于测量性能。
#ifndef _DEFAULT_SOURCE
#define _DEFAULT_SOURCE // glibc：使 syscall() 的声明可见，必须放在头文件之前。
#endif
#include <cerrno>       // errno、EINTR、EBADF、EIO：失败原因的符号名称。
#include <cstddef>      // std::size_t：表示字节数的无符号整数类型。
#include <cstdio>       // printf、perror：显示结果与诊断信息。
#include <sys/syscall.h> // SYS_getpid、SYS_write：系统调用号，避免手写架构相关数字。
#include <unistd.h>     // syscall、STDOUT_FILENO：通用调用入口与标准输出 fd。

int add(int a, int b) {
    // 纯粹对两个整数计算；这个操作本身不需要操作系统提供特权服务。
    // 编译器可能把它内联，所以不能把源码函数数目当成机器 CALL 指令数目。
    return a + b;
}

// 将 data 指向的 count 个字节交给内核，全部写完返回 true。
// const char*：可以移动指针，但不能通过它修改指向的字符。
bool write_all(int fd, const char* data, std::size_t count) {
    while (count > 0) {
        // syscall 的结果类型是 long；SYS_write 的成功结果是本次写入的字节数。
        // 即使只写一行，也按“可能短写”的接口规则处理，不能假定一次写完。
        const long written = ::syscall(SYS_write, fd, data, count);
        if (written == -1) {
            if (errno == EINTR) {
                // 该次调用在写入字节前被信号打断：重试尚未写出的同一段。
                continue;
            }
            return false; // 其它错误交给调用者报告，不无限重试。
        }
        if (written == 0) {
            // 对本例非空输出，零进展无法推进循环；转为明确失败避免忙转。
            errno = EIO;
            return false;
        }
        // written 已经确认是正数，才转换为无符号字节数，避免把 -1 变成大整数。
        const auto done = static_cast<std::size_t>(written);
        data += done;  // 下一次从尚未写出的字符开始。
        count -= done; // 只写剩余字节，避免把已经写出的前缀重复输出。
    }
    return true;
}

int main() {
    const int sum = add(20, 22); // 普通用户态计算；sum 应为 42。
    const long pid = ::syscall(SYS_getpid); // 明确发起 getpid 系统调用。
    if (pid == -1) {
        std::perror("syscall(SYS_getpid)");
        return 1;
    }

    // 字符数组末尾还有字符串结束符 '\0'；输出时减 1，不把结束符写到终端。
    const char message[] = "hello from SYS_write\n";
    if (!write_all(STDOUT_FILENO, message, sizeof(message) - 1)) {
        std::perror("syscall(SYS_write)");
        return 1;
    }

    // fd 是内核为本进程管理的打开资源编号；-1 不是有效的文件描述符。
    // 指针和长度仍然有效，因此这里只演示可预期的错误，不做越界或非法解引用。
    errno = 0;
    const long result = ::syscall(SYS_write, -1, message, sizeof(message) - 1);
    const int saved_error = errno; // 失败后立即保存，后面的库调用可能改变 errno。
    if (result != -1 || saved_error != EBADF) {
        std::fprintf(stderr, "unexpected result=%ld errno=%d\n", result, saved_error);
        return 1;
    }

    // pid 每次运行可能变化；这不是性能测试，也不能据此推导切换耗时。
    std::printf("ordinary add = %d\n", sum);
    std::printf("kernel returned pid = %ld\n", pid);
    std::printf("invalid fd: result = -1, errno = EBADF\n");
    return 0;
}
```

## 按程序顺序理解

**第一段：普通计算。** `add(20, 22)` 得到 42。它说明“程序能在用户态自己完成的工作”是什么；后面的 `printf` 可能最终调用写操作，但那不改变加法本身的性质。

**第二段：系统调用号。** `SYS_getpid` 是头文件提供的符号，避免写死某个 CPU 的调用号。`::` 表示使用全局命名空间的函数。成功时 `pid` 是当前进程编号；它不会因为刚才进入过内核就变成另一个进程。

**第三段：写出全部数据。** `data` 是缓冲区的起始地址，`count` 是剩余字节数。内核只承诺返回“本次实际写了多少”；`written > 0` 时向后挪指针、扣除长度。返回 -1 且 `errno == EINTR` 表示这次在写入前被中断，可重试当前剩余段。若写了一部分后受到中断，Linux `write` 可以返回正字节数，此时必须先计入进度。这个辅助函数针对本例阻塞输出；非阻塞 fd 的 `EAGAIN` 需要结合就绪等待另作处理。[write(2)](https://man7.org/linux/man-pages/man2/write.2.html)

**第四段：预期的失败。** 第二次故意使用 -1 作为 fd，内核拒绝请求，包装接口返回 -1 并设置 `EBADF`。这是普通错误返回，不是 C++ 异常，也不是故意触发未定义行为。程序先保存错误编号再输出，避免诊断代码覆盖它。

## 工程场景与常见误解

- **“一个库函数就是一次系统调用”不成立。** `printf` 可以先写用户态缓冲，累积后再交给内核；一些时间查询还可以经 vDSO 在用户态完成。vDSO 是内核映射给应用的一小段辅助代码和数据，具体支持哪些函数依架构而定。[vdso(7)](https://man7.org/linux/man-pages/man7/vdso.7.html)
- **“内核态切换就是进程切换”不成立。** 前者改变权限与执行环境，后者改变正在运行的任务。可以进入内核、完成请求，再回到同一线程；阻塞或抢占时才另外涉及调度。
- **系统调用不保证固定成本。** 入口／返回、检查、复制、等待都可能贡献耗时，但不是每项调用都会发生所有成本。例如 `getpid` 无须复制一块用户数据，也不必等待磁盘。
- **批量处理是取舍。** 日志一次写多条可能减少调用次数，但会增加缓冲、等待和退出时的处理需求。低延迟系统要在真实负载下比较吞吐、尾延迟与数据时效，不能只追求“系统调用数量越少越好”。
- **重试要按具体接口语义。** 本例只对 `write` 的 `EINTR` 重试；不能把“所有错误都重试”当成通用规则。

## 变式与口述

**变式：`getpid` 返回后还是同一个 PID，能证明没有上下文切换吗？** 不能。它只证明当前进程的身份；期间即使调度过其它任务，再恢复本进程，PID 也不会变。示例演示接口和错误处理，不是调度轨迹。

**变式：应用是 root，能否直接把一个普通函数调用变成内核执行？** 不能。账号权限与 CPU 特权级不是一回事，仍需受控入口。

**约 60 秒口述：** 用户态与内核态区分 CPU 执行权限，使应用不能随意操作内核和设备。系统调用是应用请求内核服务的受控接口：准备调用号与参数，进入内核，检查并执行服务，再返回结果。进入内核不必切换进程；只有阻塞、抢占等情形才可能另外发生任务切换。普通函数调用通常留在用户态，库函数与系统调用也不是一一对应，例如缓冲 I/O 和 vDSO。因此谈开销要说入口、检查、复制和等待等具体来源，并通过实际负载测量。
