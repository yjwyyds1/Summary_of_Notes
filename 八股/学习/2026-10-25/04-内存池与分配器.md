# 设计一个内存池：为什么热路径要躲开 malloc

← [[学习/学习导航/2026-10-25-学习导航|今日导航]] · [[八股测试/2026-10-25#CPP-POOL-001|回到测试题]] · 代码：[[学习/2026-10-25/示例代码/04_object_pool|04_object_pool 阅读版]]

## 先把词说清楚

**分配器（allocator）**：负责“要一块内存 / 还一块内存”的组件。STL 容器通过分配器拿内存，而不是直接调 `malloc`。

**内存池（memory pool）**：预先向系统要一大块内存，自己切成小块发出去，回收时留在池里复用。

**空闲链表（free list）**：池子里可复用的块用链表串起来，分配时摘一个，释放时挂回去。

**内存碎片**：外部碎片（空闲块太小、拼不起来）与内部碎片（分配了但没用完的部分）。

**`std::pmr`**：C++17 的多态内存资源，允许运行时替换分配策略（`monotonic_buffer_resource` 等）。

## 它解决什么问题

通用分配器（如 glibc malloc）要处理任意大小、多线程、长时间运行，因此有锁竞争、元数据开销、碎片整理。对固定大小的对象（订单、行情消息、连接对象），这些成本都可以省掉：

- 固定大小 → 不需要在块里找“够大的洞”，分配/释放都是 O(1)；
- 一次向系统要大块 → 减少 `brk`/`mmap` 次数；
- 从池里复用 → 地址集中，缓存命中更好。

## 一个最小可用的固定大小对象池

```cpp
template <typename T, std::size_t BlockSize>
class ObjectPool {
public:
    ObjectPool() {
        for (std::size_t i = 0; i < BlockSize; ++i) {
            free_list_.push_back(&storage_[i]);   // 初始时所有块都空闲
        }
    }

    T* acquire() {
        if (free_list_.empty()) return nullptr;
        void* slot = free_list_.back();
        free_list_.pop_back();
        return new (slot) T();                    // placement new：只构造，不分配
    }

    void release(T* object) {
        object->~T();                             // 先析构
        free_list_.push_back(object);             // 再把内存挂回空闲表
    }

private:
    alignas(T) std::byte storage_[BlockSize][sizeof(T)];   // 预留存储，尚未构造
    std::vector<void*> free_list_;
};
```

要点：

- `storage_` 必须是“原始存储”，不能用 `T storage_[N]`——那会构造 N 个对象。
- `alignas(T)` 保证每块满足 `T` 的对齐要求。
- `acquire()` 用 placement new 构造；`release()` 先析构再回收，顺序反了就是 use-after-free。

## 池的几种常见形态

| 形态 | 分配 | 释放 | 适用 |
| --- | --- | --- | --- |
| 栈式/线性（bump） | 指针前移 | 只能整体回退 | 一批任务内临时对象 |
| 固定大小空闲链表 | O(1) 摘链 | O(1) 挂链 | 订单、消息、连接 |
| 分级（size class） | 按大小选池 | 归还原池 | 通用分配器 |
| 环形/双缓冲 | 无分配 | 覆盖最旧 | 行情快照、日志 |

面试里被问“内存碎片怎么管理”，可以答：固定大小池天然没有外部碎片；分级的做法是把请求向上取整到某个 size class，用内部碎片换管理简单；真要跨 size 复用，才需要合并相邻空闲块（伙伴系统、TLSF 之类）。

## STL 分配器接口

容器只要求分配器提供 `allocate(n)` / `deallocate(p, n)`、`value_type`、比较相等，以及能复制。C++17 的 `std::pmr` 把它做成运行时多态：

```cpp
#include <memory_resource>

alignas(64) std::byte buffer[1 << 16];
std::pmr::monotonic_buffer_resource resource(buffer, sizeof(buffer));
std::pmr::vector<int> values(&resource);   // 从这个缓冲区里分配
```

`monotonic_buffer_resource` 只分配、不单独释放，整块析构时一起还——非常适合“一次请求内用完就丢”的场景。

## 边界与常见误解

**“内存池一定更快？”** 单线程、对象大小固定时通常更快；多线程共享一个池会引入锁竞争，反而不如每个线程一个池或线程本地分配。

**“池里的内存算泄漏吗？”** 池在程序结束时释放整块；对象在里面反复构造析构，不算泄漏。但要保证每个 `acquire` 都有配对的 `release`。

**“分配器能处理任意大小？”** 固定大小池不能。通用池要分级，复杂度立刻上升。

**“对象池能解决所有延迟问题吗？”** 不能。它解决“分配抖动”，不解决锁竞争、缓存失效、系统调用。

## 使用场景

- **交易系统**：订单、成交回报对象数量有限，启动时预分配，运行期只做构造/析构。
- **网络服务**：连接对象、读写缓冲区用池复用，避免频繁申请释放。
- **日志/序列化**：一块连续缓冲区，`pmr` 的 monotonic 资源很合适。

## 变式与口述总结

> 内存池先向系统要一大块，自己切块管理。固定大小对象用空闲链表，分配释放都是 O(1)，没有外部碎片，地址集中、缓存友好。STL 通过分配器接口拿内存，C++17 可以用 `std::pmr` 在运行时换策略。代价是要自己管对齐、构造析构、线程安全和容量上限。
