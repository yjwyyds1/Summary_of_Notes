# 06 · 怎样测吞吐与尾延迟

← [[学习/学习导航/2026-10-25-学习导航|学习导航]] · [[八股测试/2026-10-25#PERF-MEASURE-001 · 怎样测吞吐与尾延迟|自测题]] · [[学习/2026-10-25/05-LRU缓存|上一专题]] · [[学习/2026-10-25/示例代码/06_measure|代码阅读版]]

**吞吐**是单位时间完成的工作数；**延迟**是一次工作从起点到终点花的时间。平均值告诉你整体趋势，p99 则观察靠近最慢 1% 的位置。尾延迟常受排队、缺页、分配和调度影响。

```mermaid
flowchart LR
  A["固定输入、并发数与计时边界"] --> B["预热并多次采样"]
  B --> C["报告吞吐、p50、p99 与样本量"]
  C --> D["比较波动，再用 perf 定位热点"]
```

## 机制与边界

先定义起止点：从收到行情到完成解析，还是从进入队列到订单发出？两者不可混报。保证对比前后的输入、编译选项、并发数和机器状态相近。预热后重复测量，记录原始样本和分位数；再用 `perf stat/record`、火焰图或 `perf c2c` 检查具体瓶颈。

**什么时候有用**：优化行情解析或订单队列时，先验证功能，再报告吞吐、p50/p99 与重复运行的波动。

**不要误判**：p99 的估计方法和样本量要说明；毫秒计时不能自动代表真实交易链路延迟，测量本身也有开销。

## 为什么平均值不足以说明体验

假设做了 100 次操作，其中 99 次各花 10 微秒，1 次花 1000 微秒。平均值约为 19.9 微秒，看起来不大，却掩盖了那一次明显慢的操作。**p50** 可粗略看中间位置；**p99** 观察靠近最慢 1% 的位置。本页代码采用“最近秩”：排序后取第 `ceil(p×样本数)` 个。100 个样本的 p99 是第 99 个，所以仍为 10 微秒，最大值才是 1000 微秒。这个例子也提醒：p99 本身可能看不到最慢的 1%，报告时还要写样本量、最大值，必要时看更高分位数，且说明分位数算法。样本太少时，高分位数尤其不稳定。

测量前要先说清**一次操作从哪里开始、到哪里结束**。从网卡收到字节到解析完成，和从任务进入队列到处理完成，是两个不同指标。**吞吐**可写成“测试窗口内完成的操作数 ÷ 秒数”；延迟则记录每次操作耗时。高吞吐不自动保证低尾延迟：队列积压时每秒仍可能处理不少任务，但个别任务等很久。交易系统通常还需把排队、网络、业务处理和外部确认分段观察，不能把它们都归给某个函数。

本例只对一组**人为构造**的整数样本排序和求分位数，没有测量真实程序。做可信对比时，保持输入规模与分布、机器、编译选项和并发数一致；预热后重复测量，并报告波动。基准循环若计算结果无人使用，编译器可能优化掉工作；计时、日志和采样本身也有开销。先验证优化前后输出相同，再看重复运行的吞吐和分布，最后用 `perf` 等工具定位原因。[Google Benchmark 使用说明](https://google.github.io/benchmark/user_guide.html)解释预热和重复运行；延迟直方图可参考 [HdrHistogram](https://github.com/HdrHistogram/HdrHistogram)。

## 完整代码

```cpp
// 目的：用离线延迟样本演示 p50/p99 的一种明确的最近秩计算方式。
// 前置：这里的数据是教学样本，不是实测系统延迟。
#include <algorithm> // sort：排序样本。
#include <cassert>   // assert：验证分位数。
#include <cmath>     // ceil：计算最近秩索引。
#include <iostream>  // cout：输出结果。
#include <vector>    // vector：保存所有观测值。

int percentile(std::vector<int> samples, double p) { // 按值传参，排序不改调用者。
    assert(!samples.empty() && p > 0 && p <= 1); // 本教学函数的输入条件。
    std::sort(samples.begin(), samples.end());
    auto rank = static_cast<std::size_t>(std::ceil(p * samples.size())); // 秩从 1 开始。
    return samples[rank - 1]; // 转成从 0 开始的下标。
}

int main() {
    std::vector<int> micros(99, 10); // 99 个 10 微秒样本。
    micros.push_back(1000);           // 1 个长尾样本。
    assert(percentile(micros, 0.5) == 10);
    assert(percentile(micros, 0.99) == 10); // 最近秩定义下第 99 个仍为 10。
    std::cout << "p99: " << percentile(micros, 0.99)
              << ", max: " << percentile(micros, 1.0) << " us\n";
    // 真实测量还须说明采样窗口、请求起止点与分位数算法。
}
```

## 观察与自检

函数按值接收 `samples`，所以排序的是一份副本，不会打乱调用者保存的原始样本。`ceil(p×N)` 得到从 1 开始的秩，访问 `samples[rank-1]` 才是 C++ 从 0 开始的下标。对 100 个样本，p50 取第 50 个、p99 取第 99 个，二者都是 10；p100 取最后一个，为 1000。若空样本或无效 p 进来，`assert` 是教学前提检查；生产数据处理要明确报错，不能依赖发布构建中可能关闭的断言。

口述时先给**度量定义与样本量**，再讲平均值为什么会掩盖尾部，并指出 p99 也未必覆盖极端最大值。比较优化前后要保证工作负载与环境可比、重复测量，并先核对业务结果。代码做的是离线统计，没有进行真实微秒级计时。

## 用同一条请求区分三个数字

一条请求在队列里等 8 毫秒，实际计算花 2 毫秒，端到端延迟就是约 10 毫秒；只在计算函数周围计时会报告 2 毫秒，却完全漏掉用户感受到的排队。若测试窗口是 10 秒、完成 5000 条请求，完成吞吐是 500 条/秒。这个平均速率不告诉你每条等了多久，所以吞吐和延迟要同时报告。若请求不断到来且处理速度跟不上，队列还会增长，短时间吞吐看起来稳定也可能隐藏越来越大的等待。

分位数必须说明定义。这里的最近秩算法先排序，再取第 `ceil(p×N)` 个观测值；其他统计库可能用插值，得到略不同的数。100 条里只有一条 1000 微秒时，p99 仍可能是 10 微秒，最大值才暴露那次极端慢操作。样本越少，越不能把某个 p99 当作稳定的服务承诺；对高分位数更要有足够请求量与多次测量。

做 A/B 比较时先保证两版完成同样的工作，尤其不能让编译器把测试计算优化掉。再固定输入、并发、硬件和计时边界；预热，重复采样，保留原始分布与异常值。若新版本 p50 变好但 p99 变差，要继续分段看排队、锁等待、分配和系统调度，不能只报一项最好看的指标。
