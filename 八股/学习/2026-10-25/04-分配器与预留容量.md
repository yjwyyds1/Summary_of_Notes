# 04 · STL 分配器与预留容量

← [[学习/学习导航/2026-10-25-学习导航|学习导航]] · [[八股测试/2026-10-25#PERF-ALLOC-001 · STL 分配器与预留容量|自测题]] · [[学习/2026-10-25/03-伪共享|上一专题]] · [[学习/2026-10-25/示例代码/04_allocator|代码阅读版]] · [[学习/2026-10-25/05-LRU缓存|下一专题]]

**分配存储**只是取得可放对象的内存；**构造对象**才让对象生命周期开始。STL 容器通过分配器访问存储策略，常用实现会经 `allocator_traits` 适配。`vector::reserve(n)` 保证容量达到至少 n（如需要重分配），不会凭空创建 n 个元素。

```mermaid
flowchart LR
  A["分配器：取得原始存储"] --> B["vector 管理容量"]
  B --> C["reserve：预留空间，不创建元素"]
  C --> D["push_back：在空间中构造元素"]
  B --> E["容量不足：重新分配，旧引用可能失效"]
```

## 机制与边界

热路径若一批数据的最大数量有明确上界，可以在进入热路径前预留容量。每次 `push_back` 仍可能做对象构造；元素类型内部也可能分配。预留过大会增加内存占用，若超过原容量还使已有元素的地址、迭代器失效。对象池适合确有频繁同类分配且生命周期可控的场景，需处理容量、归还、并发和错误。

**什么时候有用**：接收已知上限的一批行情消息时，预留 vector 容量并在真实流量下核对峰值。

**不要误判**：自定义分配器涉及类型、传播与相等性契约；不能把对象池说成任何场景必然更快。

## “有空间”和“有对象”是两件事

`vector<int> prices;` 刚创建时可以没有元素，`size()==0`。`prices.reserve(3)` 让它准备至少能容纳三个 `int` 的存储，但此时仍没有三个可读取的元素；访问 `prices[0]` 仍不合法。随后每次 `push_back` 才在可用位置构造一个元素，`size` 依次变成 1、2、3。**capacity** 表示当前已经准备的容量，**size** 表示实际存在的元素个数。它们是容器接口状态，不是“堆上有几块内存”的直接计数。

分配器的角色是向容器提供取得和释放原始存储的方式，容器负责按规则构造、移动和销毁元素。容量不够时，`vector` 可能重新分配更大空间、把已有元素搬过去并释放旧存储；原有元素指针和迭代器因此可能失效。`reserve` 可以在已知上限时把这一过程提前到非热路径，但可能预留太多，占用更多内存。它也不会消除元素内部的分配，例如 `vector<string>` 中较长的字符串仍可能自己申请存储。10 月 20 日的[[学习/2026-10-20/06-vector与综合练习|vector 扩容专题]]专门解释了引用失效。

读下面计数器示例时认出 `allocate(n)` 的 `n` 是**元素数量**，不是字节数；实际存储仍交给 `std::allocator<T>`。本例 `reserve(3)` 通常触发一次 vector 存储申请，之后插入三个简单 `int` 不需要扩大 vector 容量，所以计数打印 1。这个计数只观察我们的分配器收到的调用，不能代表进程、输出库或元素内部的所有内存申请。自定义池或分配器还要处理对象对齐、归还、异常、并发和容器契约；没有实测瓶颈就不应直接上生产池。

## 完整代码

```cpp
// 目的：用计数分配器观察 vector 何时申请原始存储。
// 前置：allocator_traits 会调用符合分配器契约的 allocate/deallocate。
#include <cassert>  // assert：检查元素数量。
#include <cstddef>  // size_t：容量与字节数量。
#include <iostream> // cout：打印分配次数。
#include <memory>   // allocator：委托标准分配器实际取得存储。
#include <vector>   // vector：演示 reserve。

inline std::size_t allocations = 0; // 教学计数；仅在单线程 main 中使用。
template<class T> struct CountingAllocator {
    using value_type = T; // 容器要求的元素类型。
    CountingAllocator() = default;
    template<class U> CountingAllocator(const CountingAllocator<U>&) noexcept {}
    T* allocate(std::size_t n) { // n 是元素个数，不是字节数。
        ++allocations;
        return std::allocator<T>{}.allocate(n);
    }
    void deallocate(T* p, std::size_t n) noexcept { // 与取得的元素数量配对。
        std::allocator<T>{}.deallocate(p, n);
    }
};
template<class T, class U> bool operator==(CountingAllocator<T>, CountingAllocator<U>) { return true; }
template<class T, class U> bool operator!=(CountingAllocator<T>, CountingAllocator<U>) { return false; }

int main() {
    std::vector<int, CountingAllocator<int>> prices;
    prices.reserve(3); // 先申请足够容纳三个 int 的空间，但 size 仍是 0。
    assert(prices.empty());
    for (int p : {101, 102, 103}) prices.push_back(p); // 在已留容量内构造元素。
    assert(prices.size() == 3);
    std::cout << "allocations: " << allocations << '\n';
    // 只观察本例的 vector 存储申请，不计输出库或进程其他分配。
}
```

## 观察与自检

跟踪三个时刻：刚建 `prices` 时 `size=0`；`reserve(3)` 后 `size` 仍为 0、`capacity` 至少为 3；三次 `push_back` 后 `size=3`。不要在第二步读取 `prices[0]`，因为容量槽位还没有一个已构造的元素。`CountingAllocator::allocate` 每被容器调用一次就增计数，再委托标准分配器工作；`deallocate` 负责对应释放。这里的 `inline` 全局变量是 C++17 语法，表示本示例这一份计数状态。

口述时先分清“分配存储”和“构造对象”，再解释预留容量减少某些重新分配的机会。追问成本时指出多占空间、可能使旧引用失效，以及元素自身仍可分配。示例中的分配次数是这一个容器路径的观察，不是整个程序的分配画像。

## 把四个常见操作分开

`reserve(100)` 调整容量下限，不把 `size` 变成 100；随后可以 `push_back` 添加真实元素。`resize(100)` 则把元素数调整到 100，新增位置会按规则构造元素。`clear()` 移除元素，使 `size` 变 0，但通常不等于把容器容量全部交还系统。写 `v[50]` 前必须确认 `size>50`，只凭 `capacity>50` 不够。初学者把容量当作元素数，是使用 `vector` 时很常见的越界来源。

再看失效：若 `reserve` 请求的容量超过当前容量，vector 会重新分配，旧元素的地址、引用和迭代器不能继续使用。一个函数先保存 `int* p=&v[0]`，再调用可能触发扩容的 `reserve` 或 `push_back`，随后解引用 `p` 就可能出错。预留容量可以减少后续扩容机会，但必须在取得长期使用的元素引用之前设计好容量策略，不能把它当作“所有引用永不失效”的保证。

分配器、对象池、`reserve` 解决的问题也不同：前两者改变取得存储的策略，`reserve` 是容器预留空间的接口。要判断该优化是否值得做，先测分配次数和耗时是否真在热路径，再测改动前后的整体吞吐与尾延迟；维护一个复杂对象池本身也需要成本。
