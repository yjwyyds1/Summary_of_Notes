# 批量成交分配：先定义公平再写算法

← [[学习/2026-10-29/05-订单回报与撤单竞态|上一节]] · [[学习/2026-10-29/07-练习-行情缺口与发单|下一节]] · [[八股测试/2026-10-29|今日自测]]

> [!abstract] 这节要回答
> 三个内部客户希望分别买 5、3、2 手，外部一次只成交 5 手。你会怎样定义并实现“公平分配”？结果怎样保证整数、总量守恒且不超过各自需求？

## 先把业务和术语说清楚

交易所返回的是外部汇总订单的成交，但系统内部可能有多个客户或策略等待分配。不能把“这笔成交 5 手”简单复制给每个内部账户；那会凭空创造头寸。先定公平政策，再让整数算法满足守恒。

| 术语 | 初学者先这样理解 |
| --- | --- |
| 内部客户需求 | 多个账户或策略希望分到的订单数量。 |
| 外部成交 fill | 汇总订单在市场实际执行的数量。 |
| 按比例分配 | 每人按其需求占总需求比例获得份额。 |
| 最大余数法 | 先给整数下界，再按未取到的小数部分分配剩余单位。 |

## 从具体例子理解机制

令内部需求为 q_i，总需求 Q，外部成交 F。教学假设 0≤F≤Q 且所有数量是整数手。比例目标 Fq_i/Q 可能不是整数。先计算每人 floor(Fq_i/Q)，这些整数和不会超过 F；剩余手数按各人的余数大小分配。余数并列时规定稳定顺序，保证回放可复现。每个人分配不能超过需求；若外部多成交或输入非法，应拒绝并报警，不做默默截断。

**手推一遍：**需求 `[5,3,2]`，Q=10，F=5。未取整份额 `[2.5,1.5,1.0]`，下界 `[2,1,1]` 合计 4，剩余 1。前两位余数都是 0.5，约定小索引先拿，于是 `[3,1,1]`，总和为 5。若业务约定 FIFO，可能得到 `[5,0,0]`；两者都可满足总量，却代表完全不同的公平定义。

```mermaid
flowchart LR
  A["内部需求 q，外部成交 F"] --> B["计算比例份额 Fq/Q"]
  B --> C["先取每人整数下界"]
  C --> D["按余数和稳定次序补齐"]
  D --> E["检查上限与总量守恒"]
```

图中是本题选择的单一路径。**完整回答：**“公平”没有唯一算法，必须先确认业务约定。若选按需求比例，目标份额是 `F*q_i/Q`；先取整数下界，再把未分配的手数按小数余数从大到小分配，余数相同用明确稳定的客户次序打破。5、3、2 总需求 10，外部成交 5：初分 2、1、1，剩 1 手；前两者余数同为 0.5，约定较早客户优先，则结果 3、1、1。必须满足每人 0≤alloc≤request、总分配=min(F,Q)；真实合规和客户合同可能指定别的规则。

## 带中文注释的完整 C++17 示例

代码阅读版：[[学习/2026-10-29/示例代码/06_fill_allocation|06_fill_allocation]]；保存的 `.cpp` 为实际编译对象。先读关键状态，再逐步追踪每一次更新。

```cpp
// 目的：按比例和最大余数法分配一次外部成交，演示整数守恒。
// 前置：这里假设成交量不超过总需求，公平政策已约定为按需求比例。
// 步骤：需求 5、3、2，成交 5；先取下界再按余数分配。
#include <algorithm> // std::sort 按余数排序候选客户。
#include <iostream>  // 打印每个客户的最终手数。
#include <numeric>   // std::accumulate 计算总需求与已分配数量。
#include <stdexcept> // std::invalid_argument 表示本题输入不符合前提。
#include <vector>    // 保存客户需求、余数和结果。

std::vector<int> allocate(const std::vector<int>& want, int fill) {
    if (want.empty() || fill < 0) throw std::invalid_argument("bad fill");
    for (int q : want) if (q < 0) throw std::invalid_argument("bad want");
    const long long total = std::accumulate(want.begin(), want.end(), 0LL);
    if (fill > total || (total == 0 && fill != 0))
        throw std::invalid_argument("overfill");
    std::vector<int> out(want.size(), 0);
    if (total == 0) return out; // 零需求、零成交，不做除法。
    std::vector<long long> remainder(want.size(), 0);
    std::vector<int> order(want.size());
    std::iota(order.begin(), order.end(), 0); // 客户原始顺序作并列规则。
    for (std::size_t i = 0; i < want.size(); ++i) {
        const long long scaled = 1LL * fill * want[i]; // 教学输入很小。
        out[i] = static_cast<int>(scaled / total); // 比例份额的整数下界。
        remainder[i] = scaled % total;             // 未分到的小数部分。
    }
    std::sort(order.begin(), order.end(), [&](int a, int b) {
        if (remainder[a] != remainder[b]) return remainder[a] > remainder[b];
        return a < b; // 余数相同，原顺序靠前者先拿一手。
    });
    int left = fill - std::accumulate(out.begin(), out.end(), 0);
    for (int i : order) {
        if (left == 0) break;
        if (out[i] < want[i]) { ++out[i]; --left; }
    }
    if (left != 0) throw std::logic_error("allocation invariant");
    return out;
}

int main() {
    for (int n : allocate({5, 3, 2}, 5)) std::cout << n << ' ';
    std::cout << std::endl; // 3 1 1；不是唯一的业务公平政策。
}
```

### 按源码顺序读

1. `long long` 承载 `filled * requested[i]`，并在真实系统对范围和乘法溢出做显式检查。
2. 整数除法求下界，取模得到余数；余数相同时用较小索引先分配。
3. 只给仍未达到需求的账户额外 1 手，最后核对总量守恒。
4. 示例只实现离线教学分配，未处理跨成交批次和账户约束。

## 与真实 C++ 项目怎样连接

面试中先反问公平规则、最小交易单位、能否跨账户合并、部分成交如何滚动。工程实现应把规则版本、输入需求、外部 fill ID、最终分配和余数并列决议写入可审计记录，便于重放与对账。FIX AllocationInstruction 是后交易分配的一个标准消息模型，但具体券商流程要另核对。

### 前提、边界与容易说错的地方

比例算法未考虑费用、价格、不同客户风控限制和跨批次长期公平性。若一次 fill 大于总需求，示例拒绝；真实系统可能有新的分配规则但不能擅自决定。时间优先的撮合规则解决交易所订单先后，内部客户分配公平是另一层问题。

不能把教学比例算法说成交易行业统一规定；外部执行成本、账户限制、最小交易单位和公平政策都可能影响实际分配。

## 面试口述与自检

**30–90 秒口述：**先说公平必须定义；给出比例+最大余数这一个方案；最后检查整数、每人上限、总量守恒、确定性并列规则和可审计记录。

**自己再推一遍：**若需求 `[1,1,1]`、成交 2，按本题并列规则谁拿到？为何不能分别四舍五入 2/3？

**继续追问：**追问：为什么直接四舍五入每个人的比例不行？总和可能小于或大于实际成交量；先取整、再按剩余名额分配才能保持总量。
