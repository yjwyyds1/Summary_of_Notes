# 练习：行情缺口时阻止新订单

← [[学习/2026-10-29/06-批量成交分配|上一节]] · [[八股测试/2026-10-29|回到自测]] · [[八股测试/2026-10-29|今日自测]]

> [!abstract] 这节要回答
> 快照序号 200，随后收到 201、202、204；策略在 204 后发来一笔新买单。写出可信标记与是否允许新单的判断，恢复后又该怎样重新开放？

## 先把业务和术语说清楚

做出一个“序号不连续”布尔值只完成了监测，工程系统还要决定策略怎样使用它。这里把行情与交易网关连在一起，练习一个明确但可替换的安全策略：本地簿不可信时暂停依赖它的新单。

| 术语 | 初学者先这样理解 |
| --- | --- |
| fail closed | 关键输入不可验证时保守阻止新风险暴露。 |
| 恢复条件 | 重新得到可信快照并接上连续增量，同时完成业务检查。 |

## 从具体例子理解机制

本地价位簿维护 last_seq 和 trusted。收到预期的下一序号时推进；跨过一个号码时设 trusted=false。网关在调用策略发单入口前检查 trusted 与其他风控条件。恢复时重新抓取快照、衔接缓冲增量并检查连续性，才能重开。旧订单的成交/撤单回报属于独立通道，仍要正常处理和对账。

**手推一遍：**快照 200：trusted=true。201 后 last=201，202 后 last=202。204 到来时 `204 > 202+1`，trusted=false，last 保留 202；新订单被拒。加载新快照 210 后如果恢复流程确认连续，trusted=true，再允许新订单。这里故意不把 204 偷偷补成 203。

```mermaid
flowchart LR
  A["快照 200"] --> B["连续 201、202"]
  B --> C["收到 204，缺 203"]
  C --> D["簿标记不可信"]
  D --> E["阻止依赖该簿的新单"]
  E --> F["新快照+连续增量恢复"]
```

图中是本题选择的单一路径。**完整回答：**200 快照后 201、202 可依次应用；204 相对本地 202 缺 203，应把这个品种的行情簿标为不可信，并按事先定义的风控策略阻止依赖该簿的新单。不能仅把序号改成 204 就继续交易。重新获取快照并接上后续增量，检查数据源与本地状态一致后再允许发单；现有在途订单的撤单/查询通道应按系统策略单独处理，不能把“停新单”等同于“丢弃订单回报”。

## 带中文注释的完整 C++17 示例

代码阅读版：[[学习/2026-10-29/示例代码/07_gap_gate|07_gap_gate]]；保存的 `.cpp` 为实际编译对象。先读关键状态，再逐步追踪每一次更新。

```cpp
// 目的：综合演示行情序号缺口与“暂停依赖该簿的新单”。
// 前置：仅为单品种、单更新号教学模型；真实 Binance 消息有 [U,u] 区间。
// 步骤：快照 200，收到 201、202、204，再用新快照 210 恢复。
#include <iostream> // 打印每一步是否允许新单。

class FeedGate {
    int last_seq_ = -1;     // 尚未有快照时记为 -1。
    bool trusted_ = false;  // 行情簿是否可供本题策略使用。
    bool manually_halted_ = false; // 独立的人工停发开关。
public:
    void load_snapshot(int seq) { last_seq_ = seq; trusted_ = true; }
    void on_sequence(int seq) {
        if (!trusted_ || seq <= last_seq_) return; // 不可信或旧事件不推进。
        if (seq != last_seq_ + 1) { trusted_ = false; return; }
        last_seq_ = seq; // 连续时才推进本地序号。
    }
    bool can_submit() const { return trusted_ && !manually_halted_; }
    int seq() const { return last_seq_; }
};

int main() {
    FeedGate gate; gate.load_snapshot(200);
    gate.on_sequence(201); gate.on_sequence(202);
    gate.on_sequence(204); // 203 缺失，不应把 last 改成 204。
    std::cout << gate.seq() << ',' << gate.can_submit() << std::endl; // 202,0。
    gate.load_snapshot(210); // 教学恢复；真实系统还需衔接缓存增量。
    std::cout << gate.seq() << ',' << gate.can_submit() << std::endl; // 210,1。
}
```

### 按源码顺序读

1. `on_sequence` 检查下一期望值，遇 gap 将 `trusted_` 置 false。
2. `can_submit` 同时检查 `trusted_` 和独立的停发开关。
3. `load_snapshot` 在教学模型中恢复可信；真实接入还要缓存事件与核对快照衔接。
4. 示例不处理已经发送的订单回报，不能据此省略订单状态机。

## 与真实 C++ 项目怎样连接

面试时可以将它画成 Feed → Local Book → Strategy → Risk Gate → Order Gateway。说明两条故障处理线：行情不可信影响新单授权；订单回报持续流入并需要恢复对账。把这两条混成一个总开关会造成“停发以后也不记成交”的危险设计。

### 前提、边界与容易说错的地方

本练习只检查单个品种的一串单更新号，不是完整 Binance `[U,u]` 区间算法。若策略能独立于该行情做撤单或风控减仓，是否允许应由业务规则明确规定。不可把“演示重新加载快照”当作实际网络恢复实现。

停新单是本题假定的保守策略，实际系统按行情依赖关系、交易规则和风险政策决定作用范围；不要对所有策略作绝对规定。

## 面试口述与自检

**30–90 秒口述：**先判 204 跳过 203，撤销本地簿可信状态；依赖该簿的新单停发；通过新快照与连续增量恢复后再放开；已有订单的回报照常处理。

**自己再推一遍：**若收到重复的 202，应推进序号吗？如果停发期间旧订单成交了，订单状态与风险预留要不要更新？

**继续追问：**追问：gap 时还能处理已有订单的成交报告吗？必须继续按订单状态协议处理，不能让风控停发开关抹掉已发生的成交。
