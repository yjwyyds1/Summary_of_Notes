# 性能问题：没有测量就没有优化

← [[学习/学习导航/2026-10-28-学习导航|今日导航]] · [[八股测试/2026-10-28#PERF-PROFILE-001|回到测试题]] · 代码：[[学习/2026-10-28/示例代码/02_perf_benchmark|02_perf_benchmark 阅读版]]

## 先把词说清楚

**吞吐（throughput）**：单位时间处理多少请求/消息。

**延迟（latency）**：单个请求从到达到完成的时间。

**尾延迟（tail latency）**：p99、p999——最慢的那 1%、0.1% 的延迟。平均值会掩盖抖动。

**profiler**：采样或插桩程序运行状态，告诉你时间花在哪。

**火焰图（flame graph）**：把采样栈聚合成宽度可比的图形，越宽越耗时。

## 它解决什么问题

“感觉慢”不是问题描述。优化前要回答：慢在哪个路径、慢多少、目标是多少。否则很容易优化了不重要的 5%，还引入 bug。

## 四个基本问题

1. **测量对象是什么？** 吞吐还是延迟？p50 还是 p99？
2. **基线是多少？** 优化前必须有一组可复现的数据。
3. **瓶颈在哪？** CPU、内存、锁、I/O、系统调用。
4. **目标是什么？** 降低 20% 还是必须进某个预算。

## 测量工具

```bash
perf stat ./app                       # 指令数、缓存未命中、分支预测失败
perf record -g ./app                  # 采样，生成 perf.data
perf report                           # 交互式查看热点
perf c2c record ./app                 # 缓存行竞争（伪共享）
```

火焰图通常由 `perf script` 导出后交给 `FlameGraph` 脚本生成。

## 微基准的五个坑

1. **没预热**：第一次运行包含页错误、缓存冷启动。
2. **结果被优化掉**：算完没人用，编译器直接删除。
3. **只跑一次**：受调度、频率、其他进程影响。
4. **数据太小**：全部在 L1 里，测不出真实内存行为。
5. **没关频率调节**：CPU 降频导致结果漂移。

对策：预热、把结果写进 `volatile` 变量、多轮取最小或中位数、用接近真实规模的数据、固定环境。

## 边界与常见误解

**“平均延迟降了就是变好？”** 要看分布。平均值下降但 p99 上升，用户体验可能更差。

**“优化一定要改算法？”** 常常是先改数据布局、减少分配、去掉热路径里的锁。

**“profiler 显示的热点就是根因？”** 采样只说明时间花在哪；因果还要结合代码与实验。

**“本地快就够了？”** 生产环境的数据规模、并发、硬件都可能不同，要在接近真实条件下验证。

## 使用场景

- **行情处理**：关注 p99 与抖动，而不是只看平均。
- **撮合引擎**：关注每条消息的处理时间与最坏情况。
- **服务端**：关注吞吐与资源利用率，用压测工具建立基线。

## 变式与口述总结

> 性能优化先测量：明确是吞吐还是尾延迟，建立可复现基线，用 perf 或火焰图找热点，一次只改一处，同条件复测。微基准要预热、防止结果被优化、多轮取样、数据规模接近真实。平均值会掩盖抖动，低延迟系统更关心 p99。

**变式：**

1. 为什么微基准要跑多轮取最小值？
2. 平均延迟下降但 p99 上升，说明什么？
3. `perf stat` 和 `perf record` 分别回答什么问题？
