## 02 std::thread、mutex 与 RAII

两个线程执行 `++count` 时会分别读、加、写。对同一个普通变量的冲突访问缺少同步属于数据竞争，行为未定义。数据竞争不能靠“多跑几遍刚好对”证明不存在。

座位例程保护 `free + used == 100`。检查是否有座位和两次更新在同一把锁内。如果把检查移到锁外，即使最后的两次写都上锁，两个线程也可能都认为最后一个位置可用。读操作也要用同一把锁，`const` 方法不会自动同步。RAII 的 `lock_guard` 在提前 return 或异常离开作用域时释放锁。

线程引用捕获要求被引用对象活到线程退出。 `join()` 等待线程结束并同步其完成，`joinable()` 检查对象是否仍关联线程，即使线程函数已结束也可能 joinable。销毁 joinable 的 std::thread 会 terminate；不要为了绕开 join 把需要访问局部对象的线程 detach。阻塞线程要先满足退出条件，再 join。join 时不能持有 worker 退出需要的锁。 [C++17 工作草案：thread](https://timsong-cpp.github.io/cppwp/n4659/thread.thread.class)

## 03 条件变量、队列与关闭协议

队列为空时，消费者要等待“有数据或服务关闭”。条件变量负责通知，真正的事实存在 `queue_` 和 `closed_` 里。邮件里给的 wait 参数是示意，`std::condition_variable` 要传 `unique_lock<std::mutex>&`：

```cpp
std::unique_lock<std::mutex> lock(mutex_);
ready_.wait(lock, [&] { return closed_ || !queue_.empty(); });
if (queue_.empty()) return std::nullopt;
```

wait 先持锁判断谓词，谓词为假时释放锁并进入等待，唤醒后重新持锁检查。即使没有通知，也可能虚假唤醒；多个消费者被唤醒时，数据也可能已被别人取走。状态检查、状态修改、谓词用同一把 mutex。先修改状态再通知，通知发生在等待之前也能通过谓词看到状态。

| 队列 | 是否关闭 | pop 行为 |
|---|---|---|
| 空 | 否 | 等 |
| 非空 | 否或是 | 取队首 |
| 空 | 是 | 返回空，消费者退出 |

入队后 `notify_one()` 通知一个消费者。关闭后 `notify_all()`，所有等待者都要有机会离开。关闭和入队共用一把锁，谁先完成状态更新就决定这条任务是否被接收。销毁队列之前，调用方须确保等待线程已退出。 [C++17 工作草案：condition_variable](https://timsong-cpp.github.io/cppwp/n4659/thread.condition.condvar)

**代码** [03_blocking_queue.cpp](代码/03_blocking_queue.cpp)。先用纸画“消费者先到”“生产者先到”“关闭前还剩一个值”三条时序。然后从空文件重写 push/pop/close，把消费者改为两个。用各自的结果容器，join 后汇总，对照输入 ID 集合确认没有丢失或重复。多消费者完成顺序可能与取出顺序不同。

## 04 超时、多锁与读写锁

| 工具 | 何时用 | 容易错在哪 |
|---|---|---|
| lock_guard | 临界区全程持有一把锁 | 无法用于需要释放再获取的 wait |
| unique_lock | wait、延迟加锁、手动提前解锁 | defer_lock 构造后还没锁，不能直接访问共享状态 |
| scoped_lock 或 std::lock | 一次获得多把不同的锁 | 混用其他手工锁序仍可能导致死锁，别重复传同一把普通锁 |
| timed_mutex + try_lock_for | 限时获取锁 | 失败后不能访问受保护数据；调度会让实际返回略晚 |
| condition_variable + wait_for | 在锁保护下等业务状态 | 返回 true 只说明谓词为真，随后还要区分关闭与可用 |
| shared_mutex | 多读者共享锁、写者独占 | 读锁下不能改状态；释放读锁再拿写锁需要重查条件 |
| recursive_mutex | 同一线程确需递归进入同一把锁 | 无法解决两把锁相反顺序，也无法代替锁外回调 |

固定超时时间下，优先使用 `wait_for(lock, duration, predicate)`。如果手写循环，计算一次基于 `steady_clock` 的绝对截止时间，再重复 `wait_until`。每次唤醒都重置等待时长可能永远超不了时。限制“抢锁时间”和限制“等待队列有空位时间”是两种契约。

## 05 所有权、异常安全与锁外调用

`unique_ptr` 默认表达唯一所有权，`std::move` 可以交出它，移动后不要解引用原指针。 `shared_ptr` 让多个调用方延长同一对象寿命，控制块同步并不保护对象字段，也不能并发修改同一个 shared_ptr 变量而不加同步。观察对象但不延长其寿命时用 `weak_ptr`，调用 `lock()` 后检查得到的 shared_ptr 是否为空。

异常路径用 RAII 释放资源，随后考虑状态。基本保证是对象仍有效，强保证是失败后原状态不变。例程先校验和准备新状态，准备成功后再一次提交。若题目规定“通知失败时状态已经生效”，要在锁内提交并取快照，解锁后再通知。回调可能抛异常、阻塞或重新进入你的类。持普通 mutex 调用一个会调回 `snapshot()` 的函数会再次请求同一把锁。只用递归锁也解决不了外部代码阻塞或回调看到半更新状态。

## 06 原子操作和共享状态

`fetch_add(1)` 是一次原子读改写，返回加之前的值。 `load()` 再 `store(old+1)` 是两次原子操作，仍可能丢更新。 `fetch_sub` 做对应的原子减法。不同原子字段的两次读取不能构成同一时刻的快照。关联字段、容器和关闭检查通常放在一个临界区。一个 atomic<bool> 不能让 queue 自己变成线程安全，也不能独立替代条件变量的同步协议。

独立统计计数可用 `memory_order_relaxed`，它保证该原子上的操作，不能发布其他普通字段。如果题目不要求调内存序，先用默认顺序或 mutex。必须理解 acquire/release 时再练“线程 A 先写数据，再 release 写标志；线程 B acquire 读到该发布值后读数据”，同时保证发布后无未同步的再次修改。

**代码** [06_atomic.cpp](代码/06_atomic.cpp)。用两个线程各取 1000 个 `fetch_add` 返回的旧值，join 后合并排序，验证覆盖 0–1999。用这条性质解释“先 load 后 store”为什么可能发重复号。

## 07 future、packaged_task 与任务边界

让任务和执行它的线程分离。 `std::packaged_task<int()>` 包装一个可调用对象，执行时把返回值或异常存进共享状态。提交者先拿一次 `get_future()`，worker 移动取得任务，在锁外执行。调用者用 `future.get()` 取结果，任务失败时重抛原异常。普通 `future` 取一次后失效，多方读取可考虑 `shared_future`。裸 thread 的函数若让异常逃逸则会 terminate。

两线程任务执行器核心流程是：锁内校验是否已停机并入队，worker 在锁内取任务、锁外执行。stop 标记关闭并唤醒，然后锁外 join。注意第二个线程创建失败时第一个可能已启动，构造失败前要关闭并 join 已启动线程。 [C++17 工作草案：packaged_task](https://timsong-cpp.github.io/cppwp/n4659/futures.task)
